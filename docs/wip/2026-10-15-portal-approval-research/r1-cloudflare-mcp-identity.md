# Cloudflare MCP portal identity and protocol research

Researched 2026-10-15. Read-only documentation research for the assigned six questions. Local worktree: `design/portable-tool-portal-hosts`, HEAD `8535fdd433dc90fed627ee7a05f63e59d58cf8ee`. No account, credential, deployment, or running-service inspection or mutation was performed. This report is the only file written.

**Result:** Cloudflare documents per-server authorization and separate upstream credentials. It does **not** document a universal forwarding guarantee for the original portal caller's signed identity or every MCP message field. All five current client documentation sets describe OAuth support; compatibility with a particular configured Cloudflare portal remains untested.

Labels: **FACT** = read directly in a primary source; **INFERENCE** = conclusion from cited facts; **UNKNOWN** = searched but not established. Confidence describes the documentation conclusion, never live runtime qualification.

**FACT, high — manual-OAuth exception:** The separate manual-client-credentials configuration explicitly requires per-user authentication and says to leave Require user auth enabled. Thus the admin-credential OAuth row must not be read as supporting manual-OAuth bot access. [Configure manual OAuth credentials](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#configure-manual-oauth-credentials).

**FACT, high:** The explicitly documented portal client-identification header is `X-Forwarded-User-Agent`. It prefers `clientInfo.name`, then HTTP User-Agent; it can be absent. The client controls it, so Cloudflare says it is unsuitable for authentication or authorization. It identifies client software, not an authenticated agent principal. [Client identity header](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#client-identity-header), evidence anchor: “client controls the value”.

**FACT, high:** Managed OAuth on an Access-protected origin returns opaque access tokens to the client. Access resolves them and sends a signed assertion to that application's origin. For an MCP server application using Managed OAuth, Cloudflare explicitly requires validating `Cf-Access-Jwt-Assertion`. [Managed OAuth, MCP server application](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/managed-oauth/#enable-managed-oauth-on-an-mcp-server-application), evidence: “must validate the Access JWT”; [token format](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/managed-oauth/#token-format), evidence: “opaque”.

**FACT, high:** For ordinary authenticated Access origin requests, identity-based JWTs carry user `email` and `sub`; service-token JWTs carry `common_name` containing that token's Client ID and an empty `sub`. Those are distinct principals. [Application token, payload](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/#payload), evidence: “Payload contents vary”; [service-token authentication](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/#service-token-authentication), evidence: “Contains an empty string”.

### If the upstream hostname itself is protected by Access

- **INFERENCE, high, conditional:** If the portal actually authenticates to the upstream hostname's Access application using that user's upstream Managed OAuth grant, the assertion at that origin describes the upstream-authenticated user. If it uses the administrator's upstream grant, the assertion describes that administrator. If it uses static upstream service-token headers, the Access assertion identifies that configured upstream service token. These follow credential selection above plus the Access token-format/payload contracts. They do not establish that portal-caller identity is separately attached.
- **UNKNOWN:** Merely creating the server registration's Access application of type `mcp` does not prove the HTTP origin is protected, nor which assertion the managed portal emits there under all modes. Registration policies govern access **through** the portal; Cloudflare warns that direct upstream URLs bypass those policies unless separately secured. The Access API also distinguishes a `via_mcp_server_portal` destination from a hostname destination. [Add server](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#add-an-mcp-server); [Access application API](https://developers.cloudflare.com/api/resources/zero_trust/subresources/access/subresources/applications/methods/get/) `ViaMcpServerPortalDestination`, evidence: “if accessed through a MCP portal”.
- **UNKNOWN:** No inspected portal contract states that the downstream user's JWT, downstream service-token ID, or a distinct portal principal is always injected into arbitrary upstream requests. In particular, the twice-evaluated bot policy does not establish forwarding of the bot credential or a bot assertion to the network origin. Configured static upstream credentials and the incoming portal bot token must not be conflated.

## 2. Repeated upstream URL registrations and authorization against guessed names

**FACT, high:** A server registration has its own ID, upstream URL, authentication type, and credential configuration. Portal tool names include the server ID. A bot needs a matching Service Auth policy on both the portal and each linked MCP-server Access app; only registrations with `on_behalf: false` can be used by service-token sessions. The documented server-level policy covers the ability to see **and call** the tools. [Create-server API](https://developers.cloudflare.com/api/resources/zero_trust/subresources/access/subresources/ai_controls/subresources/mcp/subresources/servers/methods/create/), evidence: “Unique identifier”; [bot authorization](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#connect-with-a-service-token), evidence: “see and call”; [namespacing](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#tool-and-prompt-namespacing).

**UNKNOWN:** Whether Cloudflare accepts several registration records with the **identical upstream URL** is not explicitly documented in the inspected portal guide or create-server schema. The schema's separate `id` and `hostname` fields permit that representation but do not prove that server-side validation allows it. Consequently the complete proposed setup—same URL, distinct static credentials, distinct policies in one portal—is not verified.

**INFERENCE, medium:** If duplicate-URL registration is supported, distinct registration credentials and policies fit the documented model. This inference is contingent on URL-uniqueness behavior; it is not a successful configuration receipt.

**FACT, high as documented policy; runtime unverified:** Guessing a tool name is not documented as an authorization bypass. Cloudflare explicitly describes authorization for each server the bot attempts to reach, including calling tools. It also states that explicitly disabled tools cannot be called. [Bot authorization](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#connect-with-a-service-token); [turn off tools](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#turn-off-individual-tools-or-prompts), evidence: “not be able to call”. **UNKNOWN:** Exact denial response, timing of re-evaluation after policy changes, and bypass-resistance through `portal_execute` / Code Mode have no negative runtime proof here. Hiding for context optimization is different: `search_and_execute` deliberately hides callable tools from the initial list. [Context optimization tools](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#context-optimization-tools).

**Searches / open gaps:** Read create-server API and the full portal policy/namespacing sections. Queried `site:developers.cloudflare.com "MCP" "duplicate" "server"` and `site:developers.cloudflare.com "MCP" "same upstream"`. Hits about Agents SDK `addMcpServer` deduplication concern a different product API and were not used as portal evidence. Duplicate-URL acceptance remains UNKNOWN; no account mutation was authorized or attempted.

## 4. Catalog fetching, refresh, naming, and Code Mode

**FACT, high:** At connection/registration Cloudflare validates connectivity and retrieves tools/prompts. For DCR servers, background synchronization runs about every two hours with the **admin** credential, refreshing its access token when a refresh token permits. Dashboard/API manual sync is available. Resources are not cached in that catalog: `resources/list` fetches live and omits nonresponding servers. [Add server](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#add-an-mcp-server); [synchronize server](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#synchronize-the-mcp-server), evidence: “approximately every two hours”.

**FACT, high:** Manual-OAuth servers capture capabilities during the first user authorization; background and manual capability sync do **not** refresh that captured catalog. New tools are enabled by default unless the portal-server mapping uses `default_disabled: true`. Thus a claim that every auth mode refreshes identically is false according to the docs. [Known limitations](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#known-limitations); [synchronize server](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#synchronize-the-mcp-server).

**FACT, high:** Public tool/prompt names are `{server_id}_{original_name}`; parsing splits at the first underscore, so server IDs cannot contain underscores. Aliases replace the name portion while preserving the prefix. Portal overrides take precedence over server overrides. Alias names are limited to 40 characters; active users must reauthenticate to see alias changes; upstream renaming removes that tool's alias on the next sync. [Namespacing](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#tool-and-prompt-namespacing); [aliases](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#rename-tools-and-prompts-with-aliases).

**FACT, high:** Limits documented: 80 servers per portal, 20 portals, five custom domains per portal; server/portal IDs up to 32 characters. **UNKNOWN:** No maximum tool count per server or portal was found in the portal guide, account-limits table, or create-server API. The 80-server limit is not a tool-count limit. [Account limits](https://developers.cloudflare.com/cloudflare-one/account-limits/#access), evidence: “MCP servers per portal”; [character limits](https://developers.cloudflare.com/cloudflare-one/account-limits/#maximum-number-of-characters).

**FACT, high:** Code Mode replaces upstream tool exposure with `portal_codemode_search` and `portal_codemode_execute`; model-written JavaScript runs in an isolated Dynamic Worker and calls typed upstream-tool methods. Built-in portal management tools are also documented as always available. Policies are `off`, `opt_in`, `default_on`, and `enforced`. Names are additionally sanitized into JavaScript identifiers. Upstream servers with their own Code Mode are documented as unsupported in this arrangement. [Code Mode](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#code-mode); [Code Mode tools](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#code-mode-tools); [Code Mode namespacing](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#namespacing-in-code-mode).

**FACT, high:** Context optimization has separate documented modes: `minimize_tools` strips descriptions/schemas for on-demand retrieval; `search_and_execute` hides upstream tools behind `portal_query_tools` / `portal_execute`. These are not policy denials. The guide also uses shortened `query` / `execute` names in its optimization prose, while the explicit native-tool tables use the `portal_` names. That documentation naming inconsistency should not be silently resolved into a runtime claim. [Context optimization tools](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#context-optimization-tools), [optimize context](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#optimize-context).

**Open gaps:** Per-user catalog differences versus the admin-synchronized catalog, upstream list-changed notification handling, pagination limits, tool-count ceilings, and exact catalog convergence time after admin updates are not established. The guide documents immediate refresh for user server toggles and reauthentication for alias changes; neither establishes general instantaneous upstream catalog refresh. [Enable/disable inline](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#enable-or-disable-a-server-inline), [aliases](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/mcp-portals/#how-aliases-affect-end-users).

## 6. Linked App Token and downstream delegation

**FACT, high:** Linked App Token is an Access policy selector allowing a downstream application to trust tokens issued for a configured upstream application. It works with Service Auth and can be attached only to **self-hosted** applications, not arbitrary Access application types. It is not itself a new client-side agent credential. [Linked App Token](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/linked-app-token/), evidence: “tokens issued for another application”; [limitations](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/linked-app-token/#known-limitations), evidence: “only be added to self-hosted applications”.

**FACT, high:** In the self-hosted flow, origin A receives a user JWT as `Cf-Access-Jwt-Assertion`; A explicitly forwards it as `Cf-Access-Token` to B. Access validates the linked-app rule and issues a **new B-audience** assertion at B's origin, attributing the request to the original user in audit logs. [Forward Access JWT](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/linked-app-token/#2-forward-the-access-jwt), evidence: “scoped to Application B's AUD tag”.

**FACT, high:** The SaaS-to-self-hosted variant uses an Access-for-SaaS OAuth access token in `Authorization: Bearer`. Managed OAuth's opaque client token is different: the upstream **origin** must obtain the resolved assertion and forward that assertion, rather than expecting the client to decode or reuse the opaque token as a JWT. [SaaS flow](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/linked-app-token/#saas-to-self-hosted), [limitations](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/linked-app-token/#known-limitations); [MCP linked apps](https://developers.cloudflare.com/cloudflare-one/access-controls/ai-controls/linked-apps/), evidence: “propagate the user's identity”.

**INFERENCE, high, conditional:** This can carry an original user's identity to a cooperating downstream origin **if** the documented upstream-origin forwarding and downstream policy are in place. It cannot manufacture a human identity for a machine-only service-token session, and the generic feature does not establish a separately authenticated agent identity alongside the user.

**UNKNOWN:** The managed MCP portal is not user-owned origin A. No inspected portal setting documents dynamically forwarding its inbound assertion as `Cf-Access-Token` to every configured upstream, nor a Linked App Token selector on the upstream registration's `mcp` application. The documented selector is restricted to self-hosted downstream apps. Therefore Linked App Token is not evidence that the managed portal automatically delegates the original portal caller to our upstream. The separately documented per-user upstream OAuth path remains a different contract.
