1. Domain corrections and missing decisions

• Keep authenticated principal, logical Agent, human User, resource account, delegation, provider OAuth authorization, policy and exact-call Approval distinct. A delegated call identifies the calling agent AND the represented user/account/grant; 'agent OR user' is not permission to replace the agent identity with an arbitrary onBehalfOf field.
• Existing owner identity is (issuer,userId/subject), not email or a subject alone. oauth_accounts separately binds providerId+providerSubject within zone. Access subject and Google resource subject are different identities. Multiple issuers/app identities need an explicit linking rule; do not merge by matching email.
• Current owners.allowedAgentIds is an admission relation, not evidence of one owner per agent. oauth-config.ts enforces unique subjects but does not prohibit owners' allowed-agent sets overlapping. New Agent owner cardinality, transfer and revocation are unsettled meaning.
• A generic agent→user delegation is not identical to the current OAuth authorization. Current tuple is accountId×agentId×applicationId, with authorizationId, clientId/clientBindingRevision, zone, generation and credential identity. Native Mac/API-key resources may have no OAuth authorization at all. Keep generic delegation and provider-consent lifecycle separate.
• Grant has at least independent accessState connected/replacing/disconnecting/disconnected, lifecycle active/degraded/reauthorization-required, credential/material version and policy applying/active. 'Active grant' alone loses replacement, stale-policy and unavailable-material distinctions. catalog-schema.ts:30–94.
• Agent-own→agent owner and delegated→account owner is a candidate approval-routing rule, not established by the owner's sentence. Resource/account owner, configured editor, agent administrator, actual requesting agent and actual approver are different roles. Missing approver mapping must not fall back to the requesting agent or any logged-in user. Existing readAccountPolicyView requires the account owner's issuer/subject before policyEditors permission is checked (google-permission-policy-service.ts:419–443); a new editor of somebody else's account would expand that boundary.
• Deny/Ask/Allow is not a consent mechanism. Effective admission still intersects command/runtime ceiling, compiled activity maximum, actual provider scopes/consented groups, account policy and portal policy. Ask requires applicable approval; Allow never manufactures scopes or user consent. Missing/corrupt/applying state remains unavailable, not implicit inherit/allow. Pure evaluator: tool-portal/src/google-account-policy.ts; selection/grant checks: google-oauth-permission-policy.ts:53–118 and google-operation-grant-policy.ts.
• The owner explicitly wants agent-manageable DB config; 'every change is a new proposal requiring human editor approval' is your proposed workflow, not yet a quoted requirement. Reuse desired→validated→active snapshots and scoped configuration:activate authority before inventing a separate proposal system. Agents must use an authenticated management contract with bounded edit authority, not raw unrestricted SQL that can rewrite their own ceiling/approver assignment.

2. What the current broker actually couples

A. Current selection is limited by configured per-agent/application maximum AND the compiled offered groups. Credential policy also verifies zone/account/agent/app/client binding/catalog, admitted account owner and exact scope set; it decrypts authenticated material before admitting it. See oauth-broker/src/google/google-oauth-permission-policy.ts and google-runtime-credential-policy.ts:54–158.
B. Discovery/dispatch derives a revision cohort: account, authorizationId, generation, authorizationMetadataRevision, overrideRevision, defaultsRevision, configRevision, clientBindingRevision, catalogVersion, commandTableRevision and operation. readCurrentPolicyForDispatch recomputes and deep-compares that cohort (controller/oauth/google-permission-policy-service.ts:297–373).
C. Policy change is a protocol: save next revision as applying → contain old material/runtime → activate same transition as active. If containment fails/pends, it stays applying. See google-account-policy-editor.ts:308–422; controller-runtime.ts:1724–1738 calls credentialedRuntimeManager.invalidateMaterial scoped by account/app/authorization, generation and override revision.
D. The repository transaction checks owner, old state/revision and defaults digest, conditionally updates, and appends the permission-change event on the same connection (oauth-account-policy-repository.ts:58–183; oauth-catalog-repositories.ts:155–187). Enroll/replace similarly joins account/auth/policy/events.
E. Current account policy itself is encrypted, not merely token payloads: catalog-schema.ts:83–94; google-account-policy-envelope.ts authenticates binding+override revision and matching state. Credential AAD includes account/agent/app/authorization, metadata revision, catalog/client bindings, credential, generation, owner, provider subject and zone (envelope-codec.ts:33–58,99–102,155–235). selected/requested/actual scopes are authenticated inside the credential payload too; google-credential-payload.ts checks SQL hints equal the payload.

A cloud-owned decision plus Mac custody does NOT inherently violate these invariants, but it must define the replacement for those joins and the containment/activation protocol. A cloud DB transaction cannot atomically retire a Mac runtime. An 'Allow' read followed by an awaited refresh/materialization must not outrun a newer denial. Mac outage, stale revision, replacement/disconnect and containment failure must remain closed/pending rather than accepting a cached allow. Existing local managed admission paths also must be fenced/revision-aware; cloud-only admission cannot silently be assumed.

There is a smaller ownership arrangement to compare: cloud owns Tool Portal caller policy/approvals and management access; Mac broker retains provider consent, encrypted material, actual-scope truth and its resource ceiling. Those are distinct truths intersected at execution, not necessarily duplicate ownership of one policy. A centralized management experience can operate the Mac authority through a protected versioned API without making a second writable Google-policy copy. I am not selecting it over your proposed migration.

3. Migration and why this is an irrevocable boundary decision

Moving Google POLICY truth means inventorying account ownership/aliases, agent×account×app authorizations, consent/scopes, applying/active policy snapshots, defaults activations/digests, generations and all revision references, transitions/events, credential/material pointers, current approvals and active runtimes. Decide exactly which remain Mac-owned versus become cloud-owned. Copying only Deny/Ask/Allow cells loses binding and lifecycle.

Existing encrypted policies cannot become cloud-editable by copying ciphertext rows if the cloud has neither the key nor an explicit owner-authorized policy representation/protocol. Keeping credential IDs/AAD/owner tuples unchanged avoids unnecessary token re-encryption, but changed binding metadata must be deliberately re-encrypted/reauthorized by the actual credential owner. Do not relabel an old credential with a new user/agent/app or copy old approval consumption as fresh permission.

At cutover there must be one writer per truth, a fence against old broker policy writers, a defined initial cloud revision, handling for in-flight policy transitions and runtime containment, and refusal of stale approvals/snapshots. Restoring an older Mac DB must not restore permissions or consumed dispatch authority. Existing independent stores must not each regard themselves as current. 'Irrevocable' here is ownership/persisted meaning/security-boundary change that later callers and effects rely on—not a claim that safe rollback is literally impossible. No such migration has been authorized merely by asking for DB-backed configuration, and none has run.

Storage correction: DO SQLite matches the current serialized synchronous transaction model, but 'D1 is incapable of one-use approval consumption' is too strong. Official D1 batch docs guarantee transactional rollback for failed statements; conditional SQL/CAS can encode an atomic gate. Zero affected rows is not automatically an error, so every related mutation must be guarded; an ordinary JS read/check followed by separate calls is unsafe. D1 Sessions give sequential consistency, not a distributed lock, and replicas can lag. Thus D1 would require a different proven authority implementation, not merely swapping a Drizzle driver. One schema does not guarantee equivalent transaction semantics. Sources freshly extracted: https://developers.cloudflare.com/d1/worker-api/d1-database/ (#batch, #withsession); https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/ (#transactionSync); https://developers.cloudflare.com/d1/best-practices/read-replication/. No D1 experiment was run and no backend selection is made.

Minimum proof for a migration proposal: policy update races dispatch/refresh; crash during applying/containment/activation; stale/replayed revisions and restored old DB; wrong agent/account/client/issuer substitution; actual scope/ceiling mismatch; same key concurrent approval consumption; cloud/Mac partition; and unchanged encrypted payload binding. Real credential/runtime boundary proof is separate from schema/ORM tests.
