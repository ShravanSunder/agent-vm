Remediation decisions

Three decisions decide whether the Tool Portal remediation, the sign-in revision and the cross-repository work can start: what happens to #262, the two schemas, and how large requests are bounded. Each is drawn below with its options, where the reviewers stand, and a recommendation. Smaller decisions follow in one table. Nothing here is built; all three design sets have been through three independent reviews and their corrections.

1. #262 (OD-R1) unblocks every slice's base. 2. The two schemas (RD1, OD4) unblock the Portal store and the sign-in core. 3. Large requests (RD7) unblocks only the large-request slice; everything else proceeds without it.

1. What happens to #262 (OD-R1)

The decision: merge #262 now and fix it on master in small slices, keep it open and fix it on its branch, or close it and rebuild.

Why it's open: #262 works, but it carries the six choices you rejected, and also changes to the check gates you never approved (run-check-gate.ts, vitest.config.ts, 26 added scripts). Your rules settle what the fixed code must look like, not which branch carries the fix.

What

One commit on #262 restores the gates to 38569fca and removes the 26 scripts. Then #262 merges, and the fixes land on master as small stacked PRs. No publish or deploy from master until the Portal cutover (A8).

Gain

Small reviewable slices; one base for everyone; master never runs gates you didn't approve.

Cost

Master carries the wrong storage and Node host until the store and Node host slices merge. The hold stops it reaching anything deployed.

What

Merge #262 now; the clean-build slice (A6) reverts the gates later.

Gain

One commit sooner.

Cost

Every check on master until A6 runs gates you didn't approve.

What

Fix on the 768-file branch; merge once at the end.

Gain

Master never carries the wrong code.

Cost

Every slice rebases onto a huge branch; review sees one enormous merge.

Where the agents stand: the Lead recommends reverting the gates first. The Opus second reviewer found the earlier recommendation hid the gate cost (finding O3); this option removes it. No reviewer argued for holding or closing.

If you defer: no slice can start, because its base is undecided. The design work and reviews continue.

2. The two schemas (RD1, OD4)

The decision: approve the Tool Portal's workspace-store tables and the sign-in service's tables, each with its generated migrations, before any code uses them. You set this gate yourself.

Why it's open: it is your approval gate. The designs draw every table; nothing is generated or run yet.

Tool Portal tables (RD1), one database per workspace:

| Table | Holds | Key point | |---|---|---| | `store_meta` | which workspace this database belongs to; the store's security time | a database opened for another workspace refuses everything; time never goes backwards, so a used approval can't come back (security finding SEC-01) | | `proxy_token_use` | each used proxy approval until it expires | one row per use, so first use is one insert | | `batch_approval_use` | each batch approval: reserved, armed, or proven not dispatched | survives restarts, so a restart can't reuse an approval | | `membership`, `membership_removal` | today's membership records (version 1 only) | dropped at the identity cutover | | `removal_mark`, `removal_notice` | removals received from Fleet (version 2) | keyed by one subject key shared with the token |

Plus drizzle-kit as a development dependency of tool-host-core, to generate the migrations.

Sign-in tables (OD4): Better Auth 1.7.11's tables as its CLI generates them for the Drizzle adapter, with every SQL time default removed; session.organizationId; sign_in_audit; organization_admission_claim, one row per sign-in attempt; admitted_person_guard, which stops a refused sign-in from deleting someone Fleet admitted (security finding SEC-02). allowed_email and deployment_owner go, because admission moved to Fleet central.

Options: approve both as drawn; or approve with changes you name. There is no credible third option inside your rules: a key-value layout and hand-written SQL are what you rejected.

Where the agents stand: all three reviewers required the gate to be explicit; the Opus reviewer found the sign-in gate had no drawn schema (I2), now drawn. The security reviewer's two High storage findings are fixed in these tables.

Recommendation: approve both as drawn. Full detail: Portal tables and sign-in tables.

If you defer: the store slice (A2) and the sign-in core (B1) can't write code. The capability slice (A1) and the defect fixes (A4) still can.

3. Large requests (RD7)

The decision: you said large requests must be streamed or spilled, never capped. Streaming removes one copy of the request, but it does not bound memory. Accept the platform's memory as the bound, or commission a much larger design that bounds memory end to end.

Why it's open: your rule rules out a cap, but doesn't say what happens when one huge request exhausts a Worker's memory. On a Worker, that memory (128 MB) is shared by every call running in the same isolate, including other workspaces' calls.

What

Stream the parse, spill on Node to private temporary files, no Portal cap. The specification states the limit plainly: a request that exhausts an isolate ends the other calls running there.

Gain

No cap, as you asked; small design; fixes today's 4 MiB refusal.

Cost

One member's huge request can end other workspaces' calls in that isolate. A call that had armed an approval ends "ambiguous" for its client; the records stay correct. One new streaming JSON parser dependency.

What

Values streamed or spooled through validation, fingerprinting and forwarding, with admission and backpressure across requests; possibly a separate bulk runtime on Workers.

Gain

No cap and no shared failure.

Cost

A much larger design, written and reviewed separately; the large-request slice waits for it.

What

Refuse requests above a set size below isolate memory.

Gain

No shared failure; simplest.

Cost

It's a cap, which you rejected.

Where the agents stand: the security reviewer rates the shared failure High (SEC-03) and asks that it be either accepted explicitly or designed out. The review lead marks it as your decision (F1). The Advisor agrees streaming alone does not bound memory. Nobody recommends a cap.

Recommendation: A now, with the limit written into the specification, and B as later work if the shared failure ever shows up in practice. First, one correlated observation of today's deployed 502 is taken, because its cause is still unknown.

If you defer: only the large-request slice (A7) and the Portal cutover (A8) that waits on it are held.
