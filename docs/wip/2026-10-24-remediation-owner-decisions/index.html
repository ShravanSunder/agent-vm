3. Large requests (RD7)

You said large requests are streamed or spilled, never capped. Streaming removes one copy of the request but does not bound memory: the parsed request and the copies validation, fingerprinting and forwarding make must fit in the runtime's memory. On a Worker that is 128 MB per isolate, shared by every call running there, from any workspace. The security reviewer rates the shared failure High and asks that it be accepted explicitly or designed out; the review lead marks it as yours. Nobody recommends a cap. If you defer, only the large-request slice and the cutover that waits on it are held.

4. Where the Node host spills large requests (RD6)

Node can write a large request to a temporary file while parsing it. Those files must never land in the store's durable, backed-up state directory. But filling the spill disk can also fill the store's disk if they share space, and on a Mac two volumes can share one disk's free space. The security reviewer closed everything else and asks you to pick this policy.
