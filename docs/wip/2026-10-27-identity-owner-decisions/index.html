1. VM creators and cloud platforms: later

The design lets two kinds of thing log a machine in. The built-in one is the sign-in service: it gives a machine its tokens after you approve a device code. The other kind is an external issuer: something that creates VMs, such as agent-vm or a cloud platform, signs tokens for them, and you register it once. agent-vm was the only external issuer the design named. With agent-vm out of scope, no machine in this build would ever arrive with an external issuer's token.

Waiting takes these out of the first build: registering and withdrawing issuers; pre-approved and approve-each machines, with the "pending" state between them; checking an external issuer's signing keys at Fleet central; the retry key a VM's first login needs; and the Router's VM and platform token sources. None of it would be proven against a real issuer anyway, only against a test stand-in.

What stays: Fleet central still checks each token against the issuer that signed it, so a VM creator added later is one more issuer kind. That means one more token source on the Router and its check at Fleet central; device-code machines don't change. Your "one login model, expandable" (U33) still holds, and your "later we can have something that can spin up VMs and enrol them" (U31) becomes that later step.

2. Machines without systemd: device code, kept in memory

You picked "log in through an issuer" and asked: "why would this not just use an authority and in memory with login?" It can. Once VM creators and platforms wait (above), it's the only way those machines get in. Otherwise "issuer only" would leave them with no login at all.

Every machine you log in by device code gets a refresh credential: the thing it uses to renew its tokens without asking you again. Where that credential lives decides what happens when the Router restarts:

MachineWhere its refresh credential livesWhen the Router restarts
macOSEncrypted store, key in the KeychainRenews by itself
Linux with systemdEncrypted store, key from a systemd encrypted credentialRenews by itself
Anything else (proposed)Memory only, never written to diskShows a new device code. Once you approve it, it's the same machine with the same sessions and workspaces.

What "the token family carries its organization and enrollment" means

When you approve a device code, the machine gets two tokens from the sign-in service. The access token lasts minutes, and the machine shows it to Fleet central. The refresh token it trades for a fresh pair before the access token runs out. Each trade issues a new refresh token, and that chain is the token family.

At every trade, the sign-in service has to know which machine this is, in which organization, and whether your approval of it still stands. If you revoked the machine, the trade has to fail. A token on its own only says who approved it, and that's you for every machine you own, so it can't tell your machines apart.

Better Auth keeps one short note on a refresh token and copies it onto each new one (it calls the note referenceId). When the first tokens are issued, we write "organization X, approval Y" there. Each trade after that reads the note and asks your organization whether approval Y is still that machine's current one:

Cost: it depends on Better Auth carrying the note across trades. The first sign-in slice proves that against version 1.7.11. If it doesn't hold, we write the same note from our own device-code endpoints.

What "machines see only their workspaces, with gaps marked" means

This enforces a rule you set on 26 October (U29): "if a machine not enrolled in a workspace or cant communicate with it … they dont know about the rest." Today every connected Router receives the whole Fleet: every workspace, board and project. The filtered view stops that.

Fleet sends a Router data three ways: a list of workspaces, a full copy, and every change since that copy, numbered 1, 2, 3… All three get the same filter. "Gaps marked" is about those numbers. Fleet and the Router treat a missing number as lost data (fleet_feed_store.rs:113–123). Suppose Fleet just left out change 7 because it's about Client. M1 would see 6 and then 8, and couldn't tell "hidden from you" from "lost". So Fleet sends "7: withheld", a number with nothing in it:

NumberWhat Fleet storesWhat M1 receives
6Task added in PersonalTask added in Personal
7Project added in Client7: withheld
8OSS renamedOSS renamed (name only)

When you change what a machine serves, its copy follows. A workspace it now serves arrives as a fresh copy. One it no longer serves is deleted from its copy. One you drop to talk-only keeps just its name. A machine that was offline gets the same correction when it reconnects.

Why a machine is claimed for an organization only after you approve it

A machine belongs to one organization, for good ("a single router only belongs to one organization", U27). Fleet records that once, in a list that is never rewritten. The question is when it's written. If it were written when a machine asks to log in, before you approve, then a login you deny would still lock that machine into the organization forever. And anyone who knew a machine's ID could start a login just to lock it into the wrong one. So the record is written only after you approve, and a denied login leaves nothing behind.

Why logging a machine in again cuts off its old connection

One machine, one live login. You might approve a new login for a machine after rebuilding it, or because you think its old credential leaked. Either way, anything still connected with the old login is cut off at once, so the old credential stops working immediately, not minutes later. The machine's sessions, workspaces and boards carry over to the new login, because they belong to the machine, not to the login. The reviewers found that the earlier design let the old connection keep registering sessions and getting tokens; this closes that.
