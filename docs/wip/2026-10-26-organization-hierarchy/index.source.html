Organization hierarchy

Everything sits in one containment tree: deployment → organization registry → organization (its fleet) → workspace → board → project. A person is the only thing above the organizations: one account in the deployment, admitted to any number of organizations. Every Fleet machine, bot, Fleet harness session, workspace and project belongs to exactly one organization, and nothing is shared or sent across organizations. Where a session runs (its host or VM and its room) is a separate view from what it belongs to.

**Decided 2026-10-26:** 1. One shared Fleet central, with one fleet per organization. 2. A Fleet machine sees only the workspaces it is allowed in, plus the ID and name of workspaces paired with them. 3. A Fleet machine belongs to exactly one organization, enforced when it is enrolled. 4. Communication happens only between workspaces of one organization. 5. Nothing is shared or sent across organizations. 6. A person can join any number of organizations; bots and Fleet harness sessions can't. **Still open:** [whether a host or VM is limited to one organization too, and two storage and deployment choices](#open-questions). Where a session runs: a separate view

The tree says what a session belongs to. Placement says where it runs. They are different questions, and neither is derived from the other: a session's workspace comes from its project, never from its machine, folder or room.

- **Isolation unit (F-34):** each host or VM is its own boundary; a host and two VMs are three. Nothing is derived from hardware. - **Fleet machine (E6):** one Router installation that was enrolled. The Router is the program; the Fleet machine is its enrollment. - **Isolation record, the "room" (E13):** what launched the session says where it runs (`Host`, `ProcessSandbox`, `Container` or `Vm`). It is recorded, never proven, and in the first round nothing is refused because of it (R23). Each machine's **shared bucket** (E14) shows which workspaces have had `Host` sessions on it. **Settled:** a Fleet machine's enrollment belongs to exactly one organization (today), and inside it the machine serves several workspaces through machine allowances (U6; you turned down one machine per workspace). Its host or VM is recorded separately and not proven. **Not settled:** whether the host or VM a Fleet machine runs on is also limited to one organization. D-15 (held by F-34) says a machine we run serves exactly one boundary, but which scope that boundary is ("owner scope", still a proposed name in Q-B13) was never fixed as the organization, and nothing makes one enrollment equal one host or VM. This is [the first open question](#placement-choice), not one of your six decisions.

One example, end to end

1. **Alice is one person** with one sign-in account. O1's owner adds her email to O1's allowlist, and O2's owner adds it to O2's. She signs in to each separately, and each sign-in session is for one organization. 2. **O1's owner enrolls Fleet machine M in O1.** The enrollment belongs to O1 from then on, until it is revoked or expires. That an owner's login does this is decided; how the login works is proposed. Today, `codex-router fleet enroll` uses the operator's token, not a browser. 3. **The owner creates workspace W1, board B1 in it, and project P1 on B1**, and gives M a machine allowance for W1. M can now see W1's records, and no other workspace's. 4. **A Fleet harness session starts on M for project P1.** M registers it with O1's fleet. P1 is in W1, M is enrolled in O1 with an allowance for W1, so the session becomes a member of W1 with the session default persona, for its whole life. Until it is registered, the session's binding admits nothing. 5. **The session calls a tool** (sequence below). The Tool Portal accepts the token only for W1 and O1, only if the persona allows the tool, and only if no removal covers it. 6. **W1 has a workspace pair to W2.** W1's members can message W2's members, and M sees W2's ID and name only, never W2's boards, projects or tools. Anything aimed at O2 is refused. 7. **The owner removes the session's membership.** O1's fleet orders the removal and sends a notice to the Tool Portal. Once the Portal has stored the notice, every older token for that session in W1 is refused. While the notice is still on its way, the token's grant expiry is the backstop.

What your six decisions change

| Decision | What changes | What does not follow | |---|---|---| | One shared Fleet central, one fleet per organization | Workspace, board, project directory, names, records and feed are scoped to their organization; each workspace's parent is its organization; names are unique per organization | how many databases implement an organization; moving project databases | | A Fleet machine sees only its allowed workspaces | reads, snapshots, lookups, request records and directory search return only allowed workspaces, checked at central before anything is sent; a pair shows only the other workspace's ID and name | one feed per workspace as a requirement; sending everything and filtering on the machine | | A Fleet machine belongs to one organization, enforced at enrollment | E6's enrollment binds to exactly one organization; later calls use that binding, never an organization named by an agent; its allowances are in that organization | a new kind of identity; hardware identity; a wipe or transfer procedure | | Communication only inside one organization | workspace pairs (E17) and bot collaborations (E9) only join participants of one organization; pairs keep their direction | pairs becoming two-way; tools or board writes for collaborators | | Nothing shared or sent across organizations | refuse cross-organization records, project access, messages and tasks, mailbox and forwarded effects, and Tool Portal access, on existing transport and replication paths as well as new ones | a proof of physical isolation; separating the shared sign-in account | | A person in any number of organizations; agents in one | one person, with a separate allowlist entry, sign-in session and memberships in each organization; a bot and a Fleet harness session stay in one organization, and a bot is a member of at most one workspace | a person's O1 sign-in or owner rights counting in O2 |

The one definition to revise is E6 Fleet machine: keep "one Router installation the owner enrolled", and add that its enrollment belongs to exactly one organization, with its allowances and the sessions it vouches for in that organization. E7 keeps its full session reference and its project → workspace rule.

The identity design already says every workspace belongs to one organization (E2) and already refuses creating a workspace outside the owner's command (R28). Its gap: the Program Design leaves the workspace records in the fleet-wide Fleet object, so nothing stores or enforces which organization a workspace belongs to. Your decisions fix that.
