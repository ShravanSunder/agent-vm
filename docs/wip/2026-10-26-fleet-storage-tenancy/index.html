Fleet central storage

The identity design separates organizations for identity only: memberships, bots, sessions and allowances get one database per organization. Everything else that describes a workspace (its record, name, boards, projects, ADRs and the request log) stays in one fleet-wide database, and every machine reads all of it. You decided how to fix that on 2026-10-26: each organization gets its own fleet, and nothing is shared or communicated across organizations.

**Decided:** [one fleet per organization](#your-model), each Router logged in to exactly one organization and seeing only its allowed workspaces, communication only between workspaces of one organization, nothing across organizations. **Still open:** [three questions](#open-questions) that follow from it. The current setup: every database

There are three systems. Each database is SQLite: a Durable Object or D1 on Cloudflare, and a SQLite file on the Node or Tokio host. Solid boxes exist in code today. Dashed boxes are added by the identity and remediation designs. A **machine** is a computer enrolled in your fleet that runs codex-router's Router service: your laptop, a VM or a server. Enrolling it gives it an identity at central (one `machine_enrollments` row in the Registry: its service ID, label and access client). Its Router talks to central over one machine session, and the agents on that computer reach Fleet through it. "One for the whole fleet" on a box means one database for all of Fleet central, not one machine. In the identity design, an organization lets a machine work in particular workspaces through a machine allowance `{ installationId, workspaceId }`, so one machine can serve workspaces in two organizations.

How a workspace is created today

Any enrolled machine can create a workspace with any unused name. The CLI help says to "obtain the workspace owner's permission", but nothing enforces it. Central's only identity check is that the recorded machine is the one whose session sent the request. For one owner's own fleet that's consistent, because an enrolled machine is the boundary of trust. Once two customers share one central, it isn't.

What every machine reads today

The feed and the snapshot filter only by position. Every Router caches every workspace, board, project, ADR and request-log entry in the fleet. The request log carries who asked and from which machine. With organizations, that is a cross-organization leak, and nothing in the identity design closes it.

What the identity design adds

- **New object kind:** the organization authority, one per organization, holds E1 Organization (with its owner and sign-in allowlist), bots, fleet harness sessions, memberships, allowances, workspace pairs, bot collaborations, ordered marks and the removal outbox. - **Registry:** gains the list of organizations and the per-organization fan-out of a machine revocation. - **`CreateWorkspace`:** becomes an owner command. The organization authority checks the owner, records the command and replies `Admitted`; its outbox then has the Fleet object create the workspace. If you stop being the owner in between, the workspace is still created, empty. - **Fleet object:** bound to E2 Workspace and E16 Project **unchanged**.

Decided: one fleet per organization

This is Option 3, taken further in two ways. **Each organization gets its whole fleet**: its workspaces, projects, members and the Routers enrolled in it. And **a Router sees per workspace, not per organization**: it reads only the workspaces it's allowed in. The organization registry is the only fleet-wide part, and it holds no organization's content.

The rules you set

- **No sharing and no communication of any kind across organizations.** - **A Router belongs to exactly one organization**, enforced at login. - **Communication happens only between workspaces of one organization**, through a workspace pair. A pair shows the other workspace's ID and name, never its boards or projects. - **A Router knows only the workspaces it's allowed in**, plus the ID and name of the workspaces paired with them.

How each rule is enforced

| Rule | Where | How | |---|---|---| | A Router belongs to one organization | Router login and central | Enrolling is an organization owner's login: the owner signs in to that organization on the Router, and central checks the owner guard. The Registry keeps the enrollment as it does today, plus its organization; the credential is already unique there. The Router's state root holds one enrollment, and a second `enroll` is refused until un-enroll, which revokes the credential and wipes the Router's local Fleet state. | | A session acts only in its Router's organization | central session admission | The session is bound to its credential's organization. Any call naming another organization is refused. | | A Router sees only its allowed workspaces | the organization's fleet | Each workspace has its own feed. A workspace's feed is served to a Router only while an allowance for that Router exists, checked in the same read. | | Pairs stay inside one organization | workspace pair (E17) | Both workspaces live in the same organization's fleet. A pair shows the other workspace's ID and name only. | | No communication across organizations | the organization boundary | No object reaches into another organization's fleet: no pair, bot collaboration, forward or feed crosses it. | | Workspace names unique per organization | the organization's fleet | `UNIQUE(name)` within each organization. | | Only the owner creates workspaces | the organization's fleet | The Router's `workspace_create` is removed. Creation is an owner command, committed in one transaction. |

Login binds the Router, not the computer. A second Router on the same laptop that logs in to O2 is a different Router, which your rule allows. Only "one Router per computer" would need hardware attestation, and nothing here requires it.

What this changes in the identity design

- **E2 Workspace** lives in its organization's fleet. Which organization it belongs to is where it lives, fixed for its life. - **R13:** enrolling and revoking a Router become organization-owner commands. Only creating an organization and naming its first owner stay with the fleet's operator. - **Deleted:** - the `CreateWorkspace` outbox and its "an empty workspace is still created" caveat; - the outbox that archiving needs to reach memberships; - the Registry's revocation fan-out to every organization; - the operator's enrollment commands that act across organizations. - **New:** one feed per workspace inside each organization, the Router's single enrollment with its organization, and the Router's `workspace_create` removed. - **Unchanged:** - using an approval once is still checked in the Tool Portal's store for each workspace; - recording who approved what is still a separate, later decision; - sign-in keeps its D1; - the Tool Portal keeps one store per workspace.
The three options as first drawn | Option | What it was | Why not chosen | |---|---|---| | 1. One organization per deployment | each customer runs its own central and sign-in | reverses your D2 decision; N deployments to run | | 2. An organization column on the one Fleet object | one fleet-wide database, filtered for each reader | isolation becomes a filter every future read path must remember | | 3. One Fleet object per organization | each organization's workspaces in its own object | chosen, extended to the whole fleet and to visibility per workspace |
