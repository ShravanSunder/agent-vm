Fleet central storage

The identity design separates organizations for identity only: memberships, bots, sessions and allowances get one database per organization. Everything else that describes a workspace (its record, name, boards, projects, ADRs and the request log) stays in one fleet-wide database, and every machine reads all of it. Before any schema is approved, one decision has to be made: is Fleet central shared by several organizations, and if so, is their collaboration data separated too?

**Is Fleet central shared by several organizations, and where does each organization's workspace data live?** Proposed: shared, with **one Fleet object per organization** (Option 3). The current setup: every database

There are three systems. Each database is SQLite: a Durable Object or D1 on Cloudflare, and a SQLite file on the Node or Tokio host. Solid boxes exist in code today. Dashed boxes are added by the identity and remediation designs. A **machine** is a computer enrolled in your fleet that runs codex-router's Router service: your laptop, a VM or a server. Enrolling it gives it an identity at central (one `machine_enrollments` row in the Registry: its service ID, label and access client). Its Router talks to central over one machine session, and the agents on that computer reach Fleet through it. "One for the whole fleet" on a box means one database for all of Fleet central, not one machine. In the identity design, an organization lets a machine work in particular workspaces through a machine allowance `{ installationId, workspaceId }`, so one machine can serve workspaces in two organizations.

How a workspace is created today

Any enrolled machine can create a workspace with any unused name. The CLI help says to "obtain the workspace owner's permission", but nothing enforces it. Central's only identity check is that the recorded machine is the one whose session sent the request. For one owner's own fleet that's consistent, because an enrolled machine is the boundary of trust. Once two customers share one central, it isn't.

What every machine reads today

The feed and the snapshot filter only by position. Every Router caches every workspace, board, project, ADR and request-log entry in the fleet. The request log carries who asked and from which machine. With organizations, that is a cross-organization leak, and nothing in the identity design closes it.

What the identity design adds

- **New object kind:** the organization authority, one per organization, holds E1 Organization (with its owner and sign-in allowlist), bots, fleet harness sessions, memberships, allowances, workspace pairs, bot collaborations, ordered marks and the removal outbox. - **Registry:** gains the list of organizations and the per-organization fan-out of a machine revocation. - **`CreateWorkspace`:** becomes an owner command. The organization authority checks the owner, records the command and replies `Admitted`; its outbox then has the Fleet object create the workspace. If you stop being the owner in between, the workspace is still created, empty. - **Fleet object:** bound to E2 Workspace and E16 Project **unchanged**.

Decision 1: is Fleet central shared by several organizations?

This decides where every workspace fact lives, so the column question, name uniqueness and feed isolation all follow from it. Open a card's detail button to see its diagram.

The assumption it rests on

Several organizations will share one central and its machines. Your D2 decision says yes, and so does the allowance shape ({ installationId, workspaceId }, where nothing ties a machine to one organization). If you actually mean one customer per deployment, Option 1 wins, and most of the organization machinery in the identity design should be deleted rather than built.

Why Option 3 over Option 2

This is a structural choice about who owns what and where isolation lives. Option 2 is cheaper in code today, but it turns isolation into a filter that every future read path has to remember. Option 3 makes leaking structurally impossible, and it keeps the shipped tables as they are; only their address changes.

If you defer it

The identity design's E2 binding, the codex-router identity slices and the feed design all wait. The Tool Portal remediation and the sign-in work don't depend on this and can go ahead.

What comes after (not asked yet)

These come one at a time, after Decision 1. They're listed so that you can see where the decision leads. 1. **Under Option 3: merge each organization's Fleet object and its organization authority into one database (3a), or keep them as two objects (3b)?** My lean is 3a: one SQLite database per organization with two code modules. Creating a workspace, archiving it and ending its memberships then commit in one transaction. The `CreateWorkspace` outbox goes away, and so does its "an empty workspace even if you stopped being the owner in between" caveat. 3b touches less of the shipped Fleet code. 2. **Close the Router's `workspace_create`.** Creating a workspace becomes an owner command only. This applies under every option, and the identity design currently misses it. 3. **Approvals are two different things.** Using an approval once has to be checked atomically on each call, and has to work on a standalone Node host, so it stays in the Portal's store for each workspace (`proxy_token_use`, `batch_approval_use`). Recording who approved what is a different thing, and today nothing records it: the decision lives only inside the signed token. If you want an organization-level approval audit, that record belongs in the organization's database. It would be a new feature and its own decision. 4. **The Portal keeps one store per workspace.** That matches one MCP address per workspace. Grouping by organization would push all of an organization's tool calls through one single-threaded object. 5. **Sign-in keeps one D1.** A person is one account per deployment and can sign in to several organizations, so splitting D1 by organization would split people. Rows specific to an organization are already keyed by organization. I'd revisit this if D1 approaches its size limit.
