Who can do what: persons, workspaces, personas, agents

**People sign in. Workspaces own things. Personas get access. Agents prove who they are.** - Every resource (an account, a tool, a board, a machine) has **one owner**: a person, or a shared workspace. Its owner registers and signs it in **once**, into a workspace: your Gmail into your personal workspace (still yours), the family calendar into the household. - A **persona** is a kind of agent, registered in one workspace. It gets **its own slice** of that workspace's resources, and each tool has a mode: run it, let a judge decide, ask a person, or never. - An **agent** is one running copy of a persona. A launcher enrolls it automatically. It gets the persona's slice and never more. - Agents in a workspace can **message** each other. Getting another agent to **act** is a separate permission, granted per action; the agent doing the work uses **its own** access, never the asker's. - Nothing crosses between workspaces unless someone shares it explicitly, and no agent ever works for a different person. Every claim carries one of three marks: - ✅ **Decided**: you said it. The number points to your words in `decisions-and-open-questions.md`. - 🟡 **Proposed**: the Advisors' reading of what you said. Not confirmed by you. **Push back here.** - ❓ **Open**: needs your call. The fastest check is [section 4](#scenarios): 18 situations, each with what the model says happens. If an outcome feels wrong, the model is wrong at that point.

2. The picture

Boxes are workspaces. Solid arrows show ownership and membership. The dashed arrow is an example of an explicit share. 1. **Workspace** (the ceiling): the persona can only reach resources registered in its workspace, or shared into it. 2. **Permission profile** (the slice): within that ceiling, which resources and tools the persona actually gets, and each tool's mode. You asked "or both?" The answer is both: the workspace sets the limit and the profile picks within it. Each machine or VM belongs to exactly one workspace, and so does everything on it: files, repos, caches, git and cloud logins. An agent runs only on its own workspace's machines. 🟡 Sharing hardware between workspaces means separate VMs, not separate OS users (council proposal).

3. Resources and agents working together

🟡 All proposed. This answers "resources are by agent, right?" and "can agents in a workspace get each other to do things?" **Both are true.** Your Gmail has one owner, *you*. You register it once, into your personal workspace, sign in once and revoke once; its secrets stay in the credential broker. Registering it there doesn't make the workspace its owner, so your approval policy still applies. Each persona is *granted* its own slice: `codex-worker` may only read, while `mail-assistant` may also send if you approve. So "by agent" is right about what each agent **sees**, but not about who **owns** the account. If each agent owned its own Gmail connection, you would sign in again for every agent, and there will be many agents that come and go. **Today it really is by agent:** agent-vm grants each Google account owner a list of agent IDs (`allowedAgentIds`, `google-permission-policy-service.ts:146-156`). Granting to a persona instead is **wider consent, not a rename**: future agents inherit it. The grant must say which owner, workspace, persona version and limits it covers. Each agent stays the caller and keeps its own history, and widening a persona later never widens a grant you already gave. Inside a workspace, agents message each other on the boards and threads their profiles allow. Getting another agent to **do** something takes three separate yeses: 1. May A request **this action** from B? B offers specific actions, such as "send email"; being able to message B isn't enough. 2. May B do it on this resource? This uses B's **own** slice, never A's. 3. May the result go to this audience, such as this recipient or this board? `approved` only skips the per-call human step inside those checks. An approval request shows who asked, but that's provenance; it only counts once the asker's identity is verified. Across workspaces, agents can only talk through something shared, like the household board. The message is a request, never permission, and no agent works for a different person (✅ D-17). If permission to *message* `mail-assistant` meant permission to have it *use any of its tools*, then any agent that can talk to it could get email sent, including a test agent asking it to email workspace files to an outside address. That's why messaging and requesting an action are separate: the requester needs permission for **that specific action**, and the result's audience is checked on its own. A list of "who may talk to this agent" is too broad on its own.

5. Where this is most likely wrong

These are the points where the Advisors' evidence is thinnest or today's code disagrees with the model. In one fleet, the admin and the backbone can forge identities, change personas and read plaintext. VMs and encryption don't change that. That is acceptable for a household that trusts you. It is not acceptable if a member needs privacy *from the admin*; then personal fleets with explicit sharing links are the stronger model. - agent-vm already checks a Google account's owner and allowed agent IDs before using it, and keeps credentialed runtimes apart per agent and account. That is per agent, not per persona or workspace. - Router workspaces are an organizational home, not yet a privacy boundary. - An approval answer is checked against a supplied identity, not an authenticated one (`interaction_history_store.rs:548-565`). - No production code in the tree mints MCP portal approval tokens since the OpenClaw plugin was removed (`f2fb4c05`). The signing helpers and test callers remain, and outside consumers weren't checked. Managed Hermes uses the controller ledger. Everything on this page is the target, not current behavior. To approve one exact call, the resource needs a stable operation ID from the caller. Matching by content or by time window is unsafe. How Codex, Claude Code or Dot would supply that ID is unknown. Until a harness can, protected tools stay unavailable to it. A launched agent must reach the cloud MCP gateway through Cloudflare Access with its own identity. Two candidates: a machine token plus an agent token, or a local proxy that attaches the agent's identity. Neither has been tried. agent-vm no longer runs agents (✅ D-14). The household VM still has to be created and kept running, with a launcher that may start household agents: an AgentStudio Host for terminal agents, or the Router's own host for headless ones. No product owns that today, and nothing assigns it to AgentStudio or agent-vm by default. In agent-collaboration a workspace is an ownership area; in the AgentStudio daemon (E25), it is a UI layout. One of them has to be renamed.

8. Which product owns what

🟡 This whole split is proposed. **Fleet backbone (central)** - the registry: persons, devices, machines, services, personas, agents - leases: who may write each shared store - mail delivery between installations - your inbox: approvals, asks and notices, recorded and shown - human sign-in, phone push **One installation per execution unit** (each serves one boundary) - agent sessions and launching, boards, agent-to-agent messages - which boards, workspaces and agents each persona may talk to **Host, one per execution unit** - terminals, sessions, repos, files - asks and notices from panes - launches the agents it starts in terminals **Gateway on your Mac and iPhone** - your view across your Hosts - read-only copies; commands go to the Host that owns them **Resources and credentialed runtimes** - cloud MCP gateway, Tool Portal, computer MCP services - each persona's tool slice and approval modes - the final check before a tool runs, using an approval only once - credential broker: each account signed in once, secrets never with agents - Proving who you are never grants permission. Each product keeps its own permission profiles, keyed by registry IDs. - The backbone records and delivers approvals but never decides them and never runs the action. - A name on a board post, or a session ID, never proves who is calling. - "Role" means purpose (a skill role) or, in agent-collaboration, a role assignment that gives a concrete agent specific domain authority (e.g. only a project lead creates workstreams). Access is a *permission profile*; joining a board thread is a *seat*. Access never replaces a role gate.

12. Leases

When a lease expires, writes, wakes and schedules that need it pause; reads continue; renewing resumes them. There is no queue, grace period or bypass, because "agents dont work if they not online". A lease decides who may write a shared store. It is not a time limit on a tool call or an approval.
