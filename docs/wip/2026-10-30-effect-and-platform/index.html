Effect and the platform Moving Switchboard out

What I would build, and where Effect helps

My assessment for you · 30 October 2026

Rust for Fleet and the daemon on each machine. TypeScript for Switchboard, sign-in and the web UI. Effect is a possible way to organize the TypeScript work: it can help manage concurrent calls, cancellation, connections and cleanup consistently.

The useful question is whether Effect removes enough handwritten coordination to make that code easier to maintain. I found a credible fit, but I have not built and measured competing implementations. Adoption remains unchosen.

The price of this split: we maintain two language toolchains and test the contracts between them. I would pay that cost at these service boundaries rather than split a single tool call across extra services merely to put more code in Rust.

How the services connect

Effect would live inside the TypeScript services. Signed tokens, JSON messages and acknowledgements still cross the network. Fleet keeps the authoritative decisions; Switchboard does not gain a Fleet lookup on every tool call.

Connects the machine, registers sessions and carries tool requests.

Decides membership, grants and machine/session coordination.

Authenticates people and clients; issues tokens under Fleet's decisions.

Checks tokens and approvals, then calls upstream tools. Stores approval use and removal marks.

This is a map of the intended responsibilities, not a capture of a running system. Bots also use the sign-in and tool services. The complete identity design carries their separate rules.

The useful example: several tools running at once

An agent asks Switchboard to run five tools. One tool fails, another takes too long, and the agent disconnects while results are still streaming. Our implementation must handle each of these events without confusing what happened.

  1. Read the whole valid request. A valid-looking beginning followed by malformed data must run nothing.
  2. Check access and approvals. Record the one-use decision atomically before dispatch.
  3. Run the calls under the existing limits. One assessment failure must not incorrectly fail its siblings.
  4. Carry cancellation to the upstream adapter. A request to stop is different from proof that an external action never happened.
  5. Keep connections alive through the result stream. Close readers, clients and temporary files when the response finishes, fails or is cancelled.

Today we must express this coordination ourselves. Effect supplies a common execution model for lifetimes, child work and errors. That is its strongest potential contribution here. It is useful only if it simplifies these paths while preserving their behavior.

What changes with Effect

Dependency wiring

Pass the required database, clock, crypto and transport interfaces into the core.

Connections and cleanup

Use carefully placed try/finally, abort listeners and response-body completion handlers.

Failures and concurrent work

Keep closed result unions and explicitly settle each call before combining results.

What we pay

Less new machinery to learn, but more lifecycle coordination code for us to keep consistent.

Dependency wiring

Context and Layer can supply those same interfaces. The public contracts can remain unchanged.

Connections and cleanup

Scopes and child fibers can give related resources one owner and compose ordinary interruption and cleanup.

Failures and concurrent work

Typed error channels and full outcomes can make local failure handling explicit. Our domain outcomes still need deliberate mapping.

What we pay

A runtime, new conventions, integration adapters and bundle/startup cost. We must measure whether it removes more code than it adds.

The comparison must be between two implementations of the same corrected design. Fixing today's missing injection, volatile state or batch-failure defect cannot be counted as a benefit that only Effect provides.

Cloudflare and Node: same rules, different hosts

The core can use Effect while Cloudflare and Node supply their own platform operations. The database logic stays with its owner: Drizzle on Durable Object SQLite for Cloudflare and on better-sqlite3 for Node.

A store decision must remain one complete synchronous transaction. Effect can wrap that operation; yielding between its individual SQL statements would change the transaction boundary. Effect also cannot turn a database transaction and an external tool action into one atomic operation.

Ordinary completion and cancellation can run cleanup. An isolate or process can disappear before any finalizer runs. Durable approval records, removal marks and restart cleanup remain necessary.
Cloudflare lifetime and clock hazards

Effect's own source warns that shared fibers can inherit a request's asynchronous context and that request-owned scheduler timers can disappear. Shared pending work therefore needs a deliberate owner. A different scheduler is not a durability guarantee.

The built-in Effect clock has live defaults. Supplying our clock explicitly is still necessary, and the current TypeScript guard cannot detect ambient time hidden inside a dependency. The full Effect clock also expects monotonic time that our present clock interface does not supply. A minimal integration can keep calling our existing clock and timer ports.

Auth and the Rust-to-TypeScript boundary

Rust Fleet still answers the authority questions: does this machine belong here, is this session active, and may this grant be issued? The TypeScript issuer authenticates the caller, asks those questions over the existing authenticated protocol, and validates the answer before issuing anything.

Effect can help the TypeScript code distinguish approved, refused and the answer is unknown. It does not decide which operation may be retried.

If Fleet may have admitted a sign-in but the reply is lost, the durable claim protecting that attempt must remain. Automatic cleanup that deletes it would be wrong. Similarly, after a tool approval is armed, cancellation cannot release it and authorize another attempt.

Keep the existing JSON and token contracts with one schema owner and real producer/consumer checks. Using Effect does not require an Effect-specific RPC protocol, a replacement Rust coordination system, or a second authentication library.

Why request identity must not become a shared service

A shared runtime can hold infrastructure with an appropriate lifetime. A person's identity, session, sign-in attempt and mutable cleanup records belong to that invocation. Caching them in a singleton service could let concurrent requests share the wrong authority or cleanup set.

Agent VM and the older MCP Portal

There are also possible future uses in Agent VM's TypeScript code: acquiring a Tool VM operation group, connecting SSH, carrying cancellation, checking approval and retiring the group. The controller would still own authority and lease decisions.

The older MCP Portal owns longer-lived HTTP sessions and upstream clients. Those resources need session or service lifetimes; closing them after one HTTP request would be wrong. Its upstream stdio connections are distinct from an inbound stdio server.

A TypeScript library does not change the remote side. Closing an SSH connection is not proof that a remote process terminated. Effect does not directly change Rust Fleet, Python agents, Hermes or VM isolation. These paths are future options, separate from the current Switchboard delivery.

My recommendation

Evaluate one complete Switchboard request lifecycle, while keeping the service boundaries and existing libraries. Keep Rust Fleet, Better Auth, Zod, Drizzle and the pinned MCP SDK. Use the experiment to judge whether Effect removes repeated coordination code and makes failure behavior easier to inspect.

Both versions must preserve cancellation, streamed-response lifetime, the unknown sign-in claim, atomic storage and the existing approval outcomes. Then compare maintained code, emitted Worker size and startup cost. An increase is a tradeoff to show you, not a result to hide.

The capability interfaces can remain plain TypeScript, so choosing Effect does not need to hold up defining them. A fair comparison does need a conforming Promise baseline built first. The old fixtures are reusable ingredients, not a ready experiment. No comparison was built or run.

What my research actually established

I inventoried 379 namespace exports, read 24 packaged agent guides and the versioned generated LLMS.md, and inspected migration/release documentation and companion package manifests. I then checked the relevant source paths for request lifetimes, cancellation, databases, auth hooks and MCP adapters.

That supports a feature map and a technical fit assessment. It does not demonstrate a smaller implementation, better performance or deployed compatibility. The public documentation site was not fully scraped; exact-version official package and repository sources were retained instead.
