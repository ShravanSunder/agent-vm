Effect and the platform Moving Switchboard out

Moving Switchboard out of Agent VM

My evidence report for you · 30 October 2026

I would extract the Switchboard and sign-in packages directly from their branch, then deal with the small shared-package release separately. Merging the whole stack into Agent VM first also imports a much larger managed-runtime switch. Moving the product out does not, by itself, justify importing that switch.

This is a source-level recommendation. A separate SDK compatibility build and release check are still needed. No merge, test, publication or deployment was performed.

What the new repository still needs

The six packages moving are auth, tool-access, tool-engine, tool-host-core, tool-host-cloudflare and tool-host-node. Two shared packages remain in Agent VM.

oauth-broker-contractsThe entire source tree is identical on master and the collapsed stack.No source port is needed. The new repository needs a matching published artifact.
agent-portal-sdkThe used production API names already exist on master, but the stack changes the concrete MCP client's protocol behavior and moves schema ownership into tool-access.API availability alone is insufficient. The modern client and its new dependency must be reviewed and published deliberately.

The current four Agent VM consumers appear able to retain their implementation while the shared SDK changes land separately. That is not proof that every old SDK client can talk to every old server: the new client is modern-only, and its cancellation behavior changes.

The options and their real cost

What changes

Take the six-package closure from the frozen branch. Keep Agent VM's existing controller, gateway and portal implementation. Port only the necessary shared SDK changes and their release inputs.

What we gain

A smaller Agent VM change and a clearer separation between moving Switchboard and adopting its managed-runtime rewrite.

What we pay

Focused extraction review, SDK compatibility validation and ordered package publication. Those are real tasks; moving directories alone is insufficient.

What runs meanwhile

Existing installed Agent VM deployments can keep their current artifacts. The new Switchboard can be built and deployed separately when its gates are satisfied.

What changes

Merge the collapsed stack into Agent VM, then extract the packages and replace their workspace dependency pins with published versions.

What we gain

The stack closes in one merge before extraction.

What we pay

The four main retained packages already change in 151 files. Ten retained package manifests depend on packages that move out. Agent VM inherits the integration and distribution work.

What runs meanwhile

Already installed deployments can stay pinned. A new build from merged-and-extracted master needs the switched implementation's published dependencies.

What changes

Use master's shared packages unchanged and publish them for the new repository.

What we gain

The smallest immediate shared-source edit.

What we pay

The passive helpers exist, but the old concrete client does not establish the intended modern MCP behavior or the current Node client's proof expectations. This is not demonstrated as equivalent delivery.

What runs meanwhile

Old Agent VM behavior remains; the new repository's complete SDK/client closure is unresolved.

Publication is different from deployment

The new repository must be able to install its dependencies. With the stack's shared-schema layout, their publication order is:

  1. Unchanged OAuth broker contracts.
  2. tool-access, including the shared schemas and refinement registry.
  3. The selected agent-portal-sdk, which now depends on access.
  4. The Node host and the rest of the moved product packages, in their dependency order.

“Publish nothing until A8” conflicts with M1 needing those published cross-repository inputs. Publishing a library so another repository can build is different from deploying or running a changed service. That distinction needs an explicit decision; no temporary linking or extra bootstrap mechanism is proposed here.

The sign-in branch is not just one folder

I checked the authored first-parent history rather than attributing the entire branch's inherited code to sign-in. Its work changes auth, person-proof contracts, management/retirement integration, Worker integration and proof tooling.

In the scoped authored non-merge history, it does not change the retained Agent VM, gateway-runtime, tool-portal or mcp-portal implementations. The branch snapshot also contains an inherited hosting base. Extracting only packages/auth would omit its integration; merging the entire snapshot would bring more than auth.

Evidence and limits

Compared master 38569fca, Switchboard 2dfea38e, sign-in 0ff6a6af and design de2e5115. Read package manifests, caller imports, the complete shared-package diff, protocol-pin and schema-preservation test source, and sign-in's first-parent history.

No compile, compatibility test, installed-package check, registry-availability check or deployment was run. My conclusion is that direct extraction is the smaller source arrangement, with SDK release and publication prerequisites still open.
