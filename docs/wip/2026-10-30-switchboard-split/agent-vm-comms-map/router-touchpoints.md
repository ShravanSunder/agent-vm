## Flow notes

- `[source]` The collaboration API is one stateless MCP service mounted at `/mcp`; its listener copies share the Host-supplied application config but use distinct loopback and Unix listeners (`collaboration-mcp/src/collaboration_api_router.rs:1-3, 134-149`; `codex-router-host/src/collaboration_runtime/collaboration_api_serving.rs:56-82`).
- `[source]` Host's internal carrier tools bypass that API socket: `mcp_server` creates `CollaborationAccess::Local`, and its local adapter invokes `CollaborationApplication` methods (`collaboration-mcp/src/mcp_server.rs:184-194`; `collaboration-mcp/src/local_collaboration.rs:35-123`). External CLIs instead discover and call the service socket (`collaboration-client/src/collaboration_client.rs:105-145`; `collaboration-client/src/api_connection.rs:42-46`).
- `[source]` Enrollment is optional at the Host composition boundary: `open_board_admission` creates a machine session only for `Some(BoardSessionInputs)`; the `None` case leaves it absent (`codex-router-host/src/collaboration_runtime/board_composition.rs:115-143`).
- `[inference]` A deployment using an enrollment endpoint ending in `/v1/session` can connect to the central route shown here. The endpoint is supplied as enrollment input, and the transport accepts multiple schemes; no source inspected here selects a live `wss://` URL.
- `[source]` Central session policy is in `collaboration-central-core`; `collaboration-central-tokio` binds and serves that router (`collaboration-central-core/src/central_router.rs:20-23, 67, 119-137`; `collaboration-central-tokio/src/native_server.rs:86-129`). This identifies code ownership, not which server adapter or deployment is currently running.
