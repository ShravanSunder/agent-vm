How agent-vm fits together

agent-vm runs as two halves joined by one private channel:

  • The host side. The controller creates and retires every VM and holds the leases. It also keeps the lasting tool-control state: exact-call approvals, and Google consent and tokens.
  • The gateway VM. Hermes, the agent framework, sends each tool call over a private socket to the Node gateway runtime, which hosts the Tool Portal and MCP Portal. The runtime applies policy, calls remote MCP servers itself, and runs commands on Tool VMs directly over SSH.
  • The channel between them. The controller opens a control session to the gateway runtime. The runtime uses it to ask for approvals, leases and credentialed commands.

Tool control therefore already spans both halves. Nothing in agent-vm talks to codex-router or Fleet today.

In code, agent-vm is one repository of 17 packages, and the controller package imports all 16 of the others. #262 adds six packages under the agent-collaboration name, still inside this repository. Ten agent-vm packages import those new packages, and two of the new packages import agent-vm back.

Everything here is read from the source at agent-vm master 38569fca, #262 2dfea38e, #263 0ff6a6af and codex-router f465808f. The repository split is still under discussion, and nothing here decides it. Three limits:

  • No running deployment was observed. Each path is what the source predicts.
  • The step from a chat message into a Hermes session happens inside the external Hermes image, which wasn't inspected.
  • The sign-in drawn here is #263's older, organization-wide version. #262 sits on top of it with a newer, workspace-scoped sign-in, and whether that one fits #262's Worker hasn't been checked.

The runtime research is the 🦉 Advisor's, from its source map. I checked its decisive anchors. The package graph is mine, read from the manifests.

Who talks to whom while it runs

Four things change how to read this:

  • The controller opens the channel, not the gateway. It fetches a signed readiness response from the gateway runtime, then opens a Socket.IO session over the VM's private ingress, checked by an Ed25519 signature and a one-use nonce. Once it's open, the guest makes requests on it: leases, approvals, OAuth actions, controller-run commands. The controller's loopback HTTP API is for operators (health, admin), not for tool calls.
  • Two kinds of command VM. A leased Tool VM holds the agent's workspace. The gateway runtime reaches it directly over SSH with a key and host pin the controller hands out. A credentialed command VM is different: the controller runs it, it gets credentials by host mediation or a read-only credential file, and it runs one command at a time.
  • Gondolin is a library, not a service. The controller calls the Gondolin adapter in its own process to create, start and stop VMs.
  • Secrets stay on the host. They come from 1Password, the environment or config. A VM sees a placeholder, and the host swaps in the real value on the way out, only for allowed hosts. Git credentials never enter a VM.
How a gateway starts, and where it can fail to

A missing or stale image stops startup, and so does an old VM that can't be safely cleaned up. The image starts both processes with no restart loop; the controller decides recovery for the whole VM. A controller restart cleans up the old VMs it recorded rather than adopting them.

The four tool kinds, call by call

The four tool kinds don't map one-to-one onto agent-vm's backends:

  • A workspace tool is a remote MCP call from inside the gateway.
  • A computer tool is a command on a local Tool VM. agent-vm has no registered-computer path through a Tunnel.
  • A per-user Google tool is a command-line tool run by the controller in a credentialed VM, not an MCP call.
  • A collaboration tool lives only on a Router host; agent-vm has no way to reach it.

The MCP connection runs inside the gateway VM. "stdio" means a child process in that VM, not on the host or another computer.

Unverified: on master, the source predicts that a tool allowed only after approval is still refused after the approval. The bridge passes on only an operation id, and the layer below insists on approval again. #262's managed backend carries the approval through. Nobody has reproduced this.

This is the tool_vm target, and the gateway runs it directly. The other two command targets are run by the controller: controller_host runs on the host itself, and the ephemeral managed VM target runs in a credentialed command VM. Nothing in agent-vm reaches a registered computer through a Tunnel.

Consent, the account's deny/ask/allow policy and the one-call approval each have their own owner, and missing consent stops a call even when an approval exists. Disconnecting removes this agent's local grant. It doesn't revoke the account at Google.

No agent-vm path reaches this. No agent-vm source names a Router, Fleet, or the collaboration MCP. The Router listens only on loopback and a private socket, so an agent in a gateway VM can't call it today.

Where tool control lives today

From the code, the controller does two kinds of work. VM work: creating, leasing and retiring VMs, handing out SSH bindings, mounting workspaces, running credentialed command VMs and host Git. Tool control: exact-call approvals, Google consent and tokens, account policy, and rechecking every controller-run action. The gateway runtime mostly does tool control, but it also runs commands on Tool VMs over SSH and keeps the run artifacts.

Which package imports which

At master there are 17 packages and 49 import edges between them. No package depends on itself through another; the package graph has no cycles. To make it drawable, I grouped the 16 non-controller packages into five families by what each package's own description says. That grouping is mine, not the code's.

Each arrow counts the imports from one family into another. Two pairs point both ways, marked "back". Neither is a package cycle. But if those families became separate repositories, the two repositories in each pair would depend on each other.

The two pairs that point both ways

  • Gateway and Tools. gateway-runtime runs the Tool Portal, so it imports tool-portal. But the Tool Portal's own trust and approval vocabulary lives in gateway-control-contracts: the trusted invocation context and principal, dispatch authority, approval reservations, and the approval id and fingerprint derivation (packages/tool-portal/src/tool-portal-service.ts:38-49). So tool control is defined in a gateway package.
  • OAuth and Shared. config-contracts imports the Google command set, OAuth account id, Google policy defaults and catalog family id from oauth-broker-contracts (for example packages/config-contracts/src/oauth-config.ts:1). oauth-broker in turn imports its config schema from config-contracts.
Every import edge at master, the controller's 16 left out

That's 33 edges. With the controller's 16, that makes the 49. Four packages import nothing from the workspace: managed-vm, control-protocol-contracts, oauth-broker-contracts and secret-management.

What #262 adds

#262 adds six packages named @agent-collaboration/…. They still live in this repository's packages/ folder; only the name says where they're meant to go. Their own graph points one way:

  • the hosts depend on the engine, and the engine depends on tool-access;
  • sign-in (auth) depends on tool-access too.

But they have edges both ways with agent-vm.

The two thick arrows are the problem for a clean split. tool-host-node imports agent-vm's agent-portal-sdk, and tool-access imports agent-vm's oauth-broker-contracts. Ten agent-vm packages, agent-portal-sdk among them, import tool-access. Moved out as they are, the two repositories would each depend on the other.

From the code, both back-edges land on packages whose job is tool control, even though they carry the agent-vm name:

  • agent-portal-sdk is the SDK that agents' generated tool bindings import.
  • oauth-broker-contracts holds the per-user Google account types.

That's an observation about what the packages do, not a decision about where they go.
