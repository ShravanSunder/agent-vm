Agent identity and workspace access

Who acts in the fleet and the Tool Portal, how each one proves who it is, which workspace it belongs to, and how its tool access is granted and taken away. This is a design. Nothing in it is built or observed yet.

How it works, in plain words

This section is the whole design in a few pictures. Everything below it, and every tab, is the detail behind these.

Who is who

Everything lives inside an organization, and nothing crosses between organizations. You add a person or a bot to an organization first; only then can it join a workspace, as a member (does the workspace's work, gets its tools) or a collaborator (only messages and tasks members). A machine, meaning a Router, belongs to one organization, and you choose which workspaces it serves. A session runs on a machine and belongs to the workspace of the project it was started for. People never hold tool tokens: they get work done by talking to a bot.

How a machine gets in

You run fleet login on the machine. It shows a short code; you approve it on the sign-in page and pick the workspaces it serves. From then on the machine renews its own short-lived token. If the machine has no secret store, it keeps the login in memory, and you approve it again after it restarts. Revoking it stops its next renewal and cuts its connection.

How a session uses a tool

A session asks its own Router for a token. Fleet central, which holds the truth about who belongs where, decides; the sign-in service mints a token that lasts minutes and names the workspace. The Tool Portal checks the token on each call without asking Fleet central again. A bot gets its token the same way, with its own credential.

Taking access away

When you remove a member, retire a bot or revoke a machine, Fleet central pushes a removal notice to that organization's Tool Portal, and the next call is refused as soon as it arrives. Token expiry is only the backstop. If Fleet central is down, no new token is issued, and work stops as the tokens run out: the system fails closed.

Starting a session on another machine

A session on your Mac can start a helper on Sunclaw for a project in its own workspace, without SSH. Fleet central checks that the session is a member, the project is in the workspace, and Sunclaw serves it, then hands the start to Sunclaw over its open connection. The answer is started, refused (nothing created) or unknown (look it up later). An offline machine is refused, never queued.

Getting off Cloudflare Access

Three steps, no half steps. First everything is built while today's login keeps running. Then, still behind Access, Fleet central accepts only the new login, and you log every machine in again. Then, in the next change, Access is removed. Each step is rehearsed on the private test stack first.

What lives where: D1 and Durable Objects

Three owners, three storage homes. The sign-in service keeps only its own records in D1. Everything per organization lives in Fleet central, as one Durable Object per organization. Everything per workspace that the Tool Portal enforces lives in one Durable Object per workspace. On Node and on Fleet's Tokio host, each home is a SQLite file instead. To be walked through it, press W and choose What lives where.

Each organization's Fleet data gets its own Fleet object (OD8, your call).
