# Agent identity and workspace access: Verification Design

How each requirement in [Requirements](requirements.md) will be shown to hold, against the [Specification](specification.md)'s obligations and the [Program Design](program-design.md)'s seams. This is a plan; nothing in it has been observed.

## Proven by: one line per requirement

| U | Your need, in short | Proven by | Stays unverified |
|---|---|---|---|
| U1 | Three kinds of identity | Every token and every recorded actor parses as exactly one of the three kinds. Anything else is rejected. | — |
| U2 | Bots prove themselves with their own credential | A bot signs in with an active credential and is accepted, as the same bot through either of two credentials. With a retired one it is refused. Its record shows the storage note. | How real bots store their secrets (accepted limit) |
| U3 | Sessions vouched for by their machine | Two real sessions get tokens through their enrolled machine, each naming itself. After you revoke the machine, neither gets anything. | Cloud VMs and agent-vm VM sessions |
| U4, U5 | Member or collaborator; a bot in at most one workspace | A second membership for a bot is refused. A bot collaborator messages with its collaboration token but can't use tools or start work. | — |
| U6 | A session belongs to its project's workspace | Start a real session for a project and see its token name that project's workspace. Its repository makes no difference. A machine not allowed for that workspace is refused, and so is a start with no project, or a helper start into another workspace (if OD1 keeps that rule). A conversation whose registration is refused is never prompted. Starting needs no sign-in. A conversation registered for one project can't be registered for another. | Who may start a session (OD1) |
| U7, U8 | Collaborators only message, across allowed pairs | A session messages a member of a paired workspace and it arrives. An unpaired one is refused. Every message, task, board write and Fleet write is checked before it happens, on every path that produces it; a pair never lets another workspace write the board, take a role or start work. A bot's message is recorded as from that bot, and a member's reply reaches only that bot. A collaboration token is refused at the Tool Portal. | Whether a bot collaboration needs your allowance (OD3) |
| U9 | Look up who belongs where | Each lookup answers correctly for a person, bot, session, workspace, machine and pending removal. | — |
| U10, U11 | Members only, within their persona | A member's allowed tool call runs. A collaborator's is refused. A session's wider named persona adds nothing beyond the default. A stricter default applies from the first call served by the deployment that carries it. | — |
| U12 | No live check; configurable lifetime, max 1 h | Tokens stop working at their grant expiry, however late they were minted. The Tool Portal answers calls while Fleet central is unreachable. | — |
| U13 | Removals pushed | Remove a member and see its very next call refused once the notice arrives. A token decided before the removal but minted after it is refused; one decided right after a persona change works. With the Portal down, or the work interrupted half-way, the removal shows pending and lands later. | — |
| U14 | Fail closed | Stop Fleet central: no new decisions, a grant already decided mints only inside its window, collaboration stops, and calls stop at grant expiry. | — |
| U15 | One owner per truth | Every membership change happens only at Fleet central. The Portal and sign-in hold no membership. Requests between them come only from the expected service. | — |
| U16 | One contract, any host | The same suites pass for Fleet central on Cloudflare and Tokio, the Portal on Cloudflare and Node, and the sign-in service on Cloudflare and Node. | The Node and Tokio hosts in production deployments; the sign-in Node host until it is built |
| U17 | No new machine keys | No code path creates or reads a machine private key. Vouching uses the enrolled connection. | — |

| U20 | People sign-in unchanged | The people sign-in design's own proof, re-run with organization admission answered by Fleet central, and each change leaving its record. | The admin freshness bound SD8 (still open in the people sign-in design) |

Another member, another organization's owner, a removed owner, a stale session, a bot and a session are each refused with nothing changed or shown. Only the fleet's operator creates organizations and revokes a machine that serves several. A change whose record can't be written doesn't happen, whichever owner holds it. | SD8, as for U20 |

## Shared observations

Several rows use the same observation. Each is described once here.

**SO1: Fleet identity journey** (needed, lasting). It belongs in `verify-codex-router` as a new journey `fleet-identity`, because Fleet central owns the truth it reads.

- **What it reuses:** the board-central journey's arrangement of a local central, its enrollment and cleanup (`references/board-storage.md:3–10, 20–39`), through its TypeScript replacement under `verification/`. The product allows only TypeScript and Rust (codex-router `AGENTS.md:3–6`), so the Python `board_central_journey.py` is neither extended nor relied on, and SO1 waits until that replacement is complete. The arrangement starts no provider and no normal Router.
- **What must be built:** a native launch part that starts a normal Router (the ordinary production code paths, under an isolated, signed debug Host and Router root on declared ports, never replacing your production Router) with real sessions on each supported path: Codex through the app-server, Claude and Cursor through ACP. It registers them for projects and reads their bindings. Dependencies: provider accounts and adapter versions on the run machine, an enrollment from Fleet's production enrollment (debug mode), the per-session ACP MCP lists through the create and restore commands, and Codex thread `config` (Codex 0.163.0's `thread/start` and `thread/resume`).
- **Not counted as proof:** a captured MCP list without a real Claude or Cursor run, or one provider path standing in for another.
- **What runs:** that Router and its sessions, a local Fleet central (Tokio, plus local workerd), the local sign-in Worker from `verify-auth`'s harness, and the Tool Portal through its production `index.ts` host entry.
- **What it drives:**
  1. enroll the machine and allow it for workspace W;
  2. start two sessions for a project in W on each path (Codex helper starts through the client's bridge into the app-server's native start), naming the project, with no sign-in; try a start with no project, a helper start from a session into another workspace, and a start from a provider that doesn't support HTTP MCP; withdraw the machine's allowance between creation and registration, and lose a create reply (never prompted, acts as no member); resend the identical registration (the original `Registered`);
  3. call a Portal tool through the forwarder from each;
  4. try posting as another session, and with a stale and a foreign binding;
  5. send messages, tasks and board writes across a paired and an unpaired workspace, on the Router holding the project, forwarded from a second Router, and as direct messages; with the pair, try a board write, a role claim and a session start; withdraw the pair and retry, including replying to a message received while the pair was active; make Fleet writes (a board, a repository attachment, a decision record) as a member and as a non-member; try creating a workspace through the Fleet write path; have a bot message a member and the member reply; read the bot's mailbox with each of its two credentials, and with another bot's token (refused); withdraw the bot collaboration and have the member reply again (refused);
  6. change a session's persona, then call at once;
  7. end one session (archive) and remove the other;
  8. revoke the machine, interrupting the fan-out once;
  9. stop Fleet central between a decision and its mint, and before a decision, and attempt a collaboration effect, both a new message and a reply;
  10. for Codex, cover a fresh start, a cold resume, a loaded idle thread rebuilt on resume, and a loaded running thread rejoined across a Router restart (an arrangement that keeps the upstream runtime alive; a cold restart can't stand in for it), checking each from the next post's recorded actor, not from the resume reply; for Claude and Cursor, each restore mode the installed adapters support (load, resume); restart the Router before and after a registration reply, and during an ambiguous creation, and resend, then form the next token and end requests from the persisted registration (organization, workspace, persona) with no other hint; try to register a recorded conversation for another project, including a project in another organization.
- **What it reads:**
  - the tool's effect counter at the controlled MCP server;
  - the Portal's refusal classes;
  - decoded token claims;
  - central's lookups, including `RemovalStatus`;
  - board records, stored writes and delivered tasks;
  - after each refusal, what that refusal promises: a start refused before creation leaves no new conversation; one refused at registration leaves a known conversation idle and unprompted, its binding inactive, with no member effect; any other refused effect leaves nothing stored or delivered.

**SO2: sign-in issuance journey** (existing `verify-auth` agent journey, to update, lasting). Its target is the local T3 sign-in Worker on real workerd, D1 and the locked Better Auth 1.7.11 (observations made at 1.7.8 count only for 1.7.8). Changes:

- Bot client credentials take their decision from a real local Fleet central.
- A bot with two credentials gets the same `principal` through either.
- The fleet-session grant mints for two sessions under central's one client, each with its own `principal`.
- Each refusal class is observed: not a member, identity not proven, machine not allowed, unavailable, and a decision past its redemption window.
- A collaboration token is minted for a bot with no membership.
- Each row of the issuer's dispatch table succeeds through the real provider and the outer release (bot workspace, bot collaboration, fleet-session grant, Fleet's service tokens for each service audience, person), and each refused combination is refused: a bot asking for a service audience, Fleet's client asking client credentials for a workspace or collaboration address, another client using the fleet-session grant, a person asking for a workspace address.
- Credential provisioning, using only Fleet's service credential, returns a secret once and the same credential with no new secret on a repeat (no rotation); a person, bot or wrong-operation token is refused; interrupting after the issuer commits and before Fleet records the reply leaves the credential usable by its retire-and-reprovision path. Disabling reports `Disabled`, then `AlreadyDisabled`.
- With no per-client resource link rows at all, an active bot and a session get tokens for their workspace; a collaborator, a wrong workspace, a wrong client kind and an unknown or disabled workspace resource are each refused; Fleet unavailable still refuses.
- On the pinned provider, a bot request runs in this order: client authentication, the decision from central inside the claim hook, claim stamping, signing, then the response release. A refusal or timeout in the hook leaves no token at all. Two concurrent requests from different bots, or for different resources, each get their own grant.
- With bot A's Basic credentials and a body `client_id` naming bot B (no body secret or assertion), the request is refused or decided for A only; central receives A's client ID and the signed `principal` is A's bot, never B's. The same holds for each supported way a client authenticates (Basic, a body secret, `private_key_jwt`).

**SO3: Tool Portal admission** (existing agent-vm host e2e suites on the production entry, extended, lasting). It covers:

- each C1 refusal class before any tool runs, read from the controlled MCP server's effect counter;
- persona narrowing: session default, an undefined persona, a narrower one, a partly wider one on a shared tool and on a tool only it allows; and a stricter default deployed while a token is live, observed on the first call each serving instance of the new deployment handles;
- removal marks: a forged notice, an unauthenticated one, an out-of-order lower one, a duplicate, notices surviving a store restart, and the retention boundary;
- calls answered while no Fleet central exists;
- approvals keyed by principal: session S2 presenting S1's approval, a bot's second credential replaying its first credential's approval, a replay after a host restart, and changed arguments under one approval are each refused; one exact effect, then zero.

**SO4: central conformance** (existing `verify-codex-router` central-runtime journey, extended, lasting). The organization authority's commands, guard, lookups, marks and outbox, and the Registry fan-out, run on native Tokio and on local workerd from one core, including restarts between each owner's commit and its outbox steps. It covers each command's record at its own owner (the organization authority; `CreateWorkspace` recorded there and applied with the Fleet object's record; `CreateOrganization` and revocation in the Registry), a command whose record can't be written at each owner, and the organization's audit view assembled from each owner when read; a `CreateWorkspace` applied once, including across a restart between its admission and Fleet's commit, and still applied when the owner changes in between; organization creation and owner naming by the fleet operator, a new organization holding its owner's email with no person bound until the first provider sign-in; a creation interrupted before the authority is initialized; a revocation committed while an organization is being created, and an old connection of a revoked machine registering in an organization created after the fan-out's snapshot (refused); the fan-out's per-organization progress across restarts; `AdmitSignIn` and `Standing`; collaboration admission decisions for each operation and refusal class; and the credential outbox (`DisableBotCredential`) across restarts. These are new named scenarios; the old aggregate journey earns no credit for them. They need the organization object, the Registry's list, the new receivers' bearer checks and the service caller on both runtimes.

**SO5: deployed check** (existing private Cloudflare deploy cycle, a new row, temporary per cycle). It covers the Tool Portal, the sign-in service and Fleet central on real Workers in the private account:

- a bot token is issued and used;
- a removal is pushed and the next call is refused;
- Fleet central is made unavailable and no token issues.

Sampling covers arrival and refusal only.

**SO6: contract round trips** (needed, lasting). Fixtures generated from the Rust contract are parsed by the Zod schemas and back, for every shape in the Program Design, including the complete `Registered` tuple and both person operations: principals and isolation kinds (including `host` with its instance ID), persona references, decisions, notices, marks at their limit, and a version the receiver doesn't know.

**SO7: service-request negatives** (needed, lasting). For each C7 edge on its real receiving entry: the right caller succeeds, also with a newly rotated key during its overlap. Each of these is refused with nothing changed: the wrong caller, the wrong scope, another receiver's audience, a body naming an organization or workspace the caller may not act for or the receiver doesn't host, a malformed body, a token whose lifetime exceeds 5 minutes, an expired credential, and a withdrawn or unknown key. This covers every C7 edge, including workspace resources, credential provisioning and disabling, and person admission. Key withdrawal is tested warm: use a key, withdraw it, then present it within and after the declared cache bound (issuer client keys 5 minutes, 10 on fetch failure; receivers' issuer keys at most 5 minutes), and with the key-set source unreachable. A repeat has only the stated effect. Described, not executed: whoever holds an unexpired service token can send another in-scope request of that kind; bodies are not signed, so no test claims to detect a changed in-scope body.
