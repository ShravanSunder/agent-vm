# Verification Design: how we'll know it works

[Requirements](requirements.md) · [Specification](2026-10-14-portable-tool-portal-hosts.md) · [Program Design](program-design.md)

This is the plan for proving the seventeen checks in the [Specification](2026-10-14-portable-tool-portal-hosts.md). Writing it proves nothing; each check is proven when its test or run passes on the real code.

**The main method is to compare old with new, through each way in.** While `@agent-vm/tool-portal` and `@agent-vm/mcp-portal` still exist (before the switch in S4), the same configuration and the same calls go to the old code and to the new pieces, and the results must match. That's how "the same as today" gets checked rather than assumed.
- **The old side is pinned to `master` commit `08f9e426`,** so the reference can't drift during the comparison.
- **The comparison runs through each of the three ways in:** agent-vm's private connection, the standalone Tool Portal's MCP tools, and the MCP proxy.

**VM tests run in GitHub CI only,** never locally. VM memory there is 2.5G (#242).

**Worker tests run twice:** first in Cloudflare's own runtime on a machine (workerd, through `wrangler`'s local mode), then on the deployed Worker. Deploying uses the owner's existing Cloudflare CLI login. Behaviour that only a real deployment shows (several copies of the Worker at once, real sign-in tokens, real Analytics Engine writes, real memory) is proven only on the deployed Worker.

| # | Check | How it's proven | It fails if… |
| --- | --- | --- | --- |
| 1 | Same tools and shapes | Old-versus-new for each way in, over a fixed set of configurations and callers: tool names, inputs, result shapes and artifact reads, compared item by item. For the proxy's `direct` mode, the expected new list is the old list plus exactly the four search tools | a tool, schema, result shape or artifact read differs, or `direct` lists anything beyond the four added search tools |
| 2 | Each client gets one of two cases, and both reach the same tools | **Real runs of both cases, by an independent Verifier,** against one workspace's portal with a catalog as large as the real one (170 tools totalling about 4.56 MB, from controlled test servers). **One server down at startup:** with one of three test servers refusing connections, the portal still starts. The plain address lists and calls the other two servers' tools, and the diagnostics name the failed one. `?tools=direct` gets 503 with the failed server's name. Then the server comes back, and the next request lists it with no restart. A build that refuses to start, or that caches the incomplete catalog, fails. **Startup, observed on its own:** on a machine, the test servers record the portal listing their tools before the portal accepts any client. On the Worker, an authenticated request that doesn't ask for tools creates the workspace's engine (`server/discover`), and the test servers record the listing during that request, before any `tools/list`, search or call is sent. **`client-deferred`:** a real client that defers (Claude Code, given the `?tools=direct` address) lists the tools, finds one, and makes a real call to a test server. The run records Claude Code's version and the settings that keep tool search on (`ENABLE_TOOL_SEARCH` not false, no custom `ANTHROPIC_BASE_URL`, and this server not exempted from deferral), and shows the client fetching every page. Deferral is proven from the client's requests to its model provider, captured before any search and again after one tool is chosen. With Anthropic's tool search, every definition is still sent, but this server's are marked `defer_loading: true` and stay out of the model's context; the chosen tool is expanded only after a search returns it ([tool search](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool)). So the test is "marked deferred, then expanded on demand", not "absent from the request", and a run that loads every definition up front fails it. Tool-search use alone doesn't count. If the client's provider traffic can't be captured, that part is recorded as unproven. **`portal-deferred`:** a real client on the plain address (the MCP SDK client, and Hermes in CI) sees only the four search tools, and finds and calls the same tool through them. The bytes of every `tools/list` page on the wire are recorded separately from the context evidence. The two clients run **at the same time against the same workspace**, and the first client's view is checked again after the second connects. The same agent connecting to the other address shows the case follows the address, not the agent. The same caller's case is checked across several requests. **On the Worker,** the same agent makes two calls in a row on one isolate through the real transport, and each runs with exactly one effect. The run shows a fresh outbound client per request and that the catalog wasn't discovered again; a build that caches the client across requests fails the second call. Permissions, approvals and results are compared between the two runs | the two cases reach different tools or give different results; a client on the plain address receives the full list; a caller's case changes between requests, or when another client connects; the portal lists a test server's tools only once a client asks; a page is over the cap; the deferring client loads this server's definitions up front, not marked deferred; a `client-deferred` client sees fewer tools than the caller may use, because its own page or tool limit cut the list |
| 3 | Hidden stays hidden | Calls to a hidden tool through each way in, by exact name, guessed name and search result, plus an allowed call as the control | a hidden tool runs or is shown |
| 4 | Same outcomes | Old-versus-new for allowed, refused, needs-approval and failed calls, result for result, including the bytes of the per-tool TypeScript helper that `describe` returns | any result differs from today's |
| 5 | One way to a tool | A deliberately wrong build that calls a backend without going through the dispatcher must fail the test, on the unauthorised effect, not on a setup error | the wrong build passes |
| 6 | Approvals | **agent-vm, in two places.** (1) **Where the one-use rule lives:** the permanent integration test `managed-mcp-approval.integration.test.ts` (#253). It runs the real private socket, production setup, S2 and the durable controller ledger: an approved write runs once and a replay adds zero; mismatched, missing and blocked grants add zero. (2) **The CI Hermes journey** in `portal-composition.hermes.e2e.test.ts`: a tool that needs approval, Hermes's native approval, the real controller decision, exactly one counted effect, with the ledger read back as used. A second guest run of the same code is a new operation: it gets its own pending challenge, it's denied, and the count stays at one. Replay isn't driven through the live VM connection: production allows one active connection per attachment and refuses a second one (`managed-plugin-attachment-policy`), and disconnecting withdraws the authority. That limit is named, not waived. **Standalone Tool Portal:** today's batch-approval tests carried over, on both routes: the approval in MCP metadata from the real Portal SDK, and in the header on the JSON route. The exact batch runs; a call outside the batch is refused; a reused approval is refused; an approval from before a restart with a new service generation is refused. **MCP proxy:** today's token tests carried over, in both forms: `portalApprovalToken` in `mcp_portal_call`, and the approval metadata on a `direct` call to a tool that needs approval. The named calls run; a missing, mismatched or reused token adds zero effects | a call runs without approval, an approval runs a call it doesn't name, an approval is used twice, or an approved call can't run |
| 7 | Credentials stay out | A secret "canary" value given to a test tool server; the test checks it never shows up in results, errors, catalogs or logs a caller can read | the canary appears anywhere a caller can see it |
| 8 | Same limits | Today's limits checked at the old entry point and its replacement: Tool Portal JSON-route requests (64 KiB passes, 65 KiB refused), with no new cap on its MCP route; Tool Portal MCP text at 4,096 bytes while the structured result is still returned; proxy tool-server responses at 4 MiB before redaction; and a proxy request over 4 MiB, which today's proxy accepts, is sent through the real Node route of both old and new and isn't refused by a new cap (the SDK's default 4 MiB body limit must not apply on a machine) | any limit moves, disappears, or is newly added |
| 9 | Managed tools unchanged | After the switch: agent-vm's full suite, its VM and Hermes tests in CI, and the private connection's `portal`, `artifact.read` and catalog operations | any managed tool, approval, private operation or controller check stops working |
| 10 | MCP 2026-07-28 clients only | The Portal SDK, on the SDK v2 client, calls `tool_portal_call` with approval metadata and reads an artifact through the replacement standalone server. A request goes on the Tool Portal's JSON route. The SDK v2 client calls the proxy and the local Worker over Streamable HTTP, and over stdio on a machine. Hermes keeps passing the CI Hermes tests through the private connection. **Raw-wire controls on each HTTP MCP route.** A test server counts effects: zero for every refused control, exactly one for the valid call:<br>• the MCP SDK v1.29.0 client's `initialize` gets 400 with `-32022` and the supported versions;<br>• a request with the `MCP-Protocol-Version: 2026-07-28` header but without its required `_meta` gets 400 with `-32602`;<br>• a missing or mismatched `MCP-Protocol-Version` or `Mcp-Method` header gets 400 with `-32020`, and so does a missing or mismatched `Mcp-Name` on `tools/call` and on `resources/read`; `server/discover` and `tools/list` without `Mcp-Name` succeed;<br>• `GET` and `DELETE` get 405;<br>• a valid call carrying an arbitrary `Mcp-Session-Id` succeeds, and no response carries one;<br>• `server/discover` advertises 2026-07-28 with `cacheScope: "private"`;<br>• every `tools/list` page carries `cacheScope: "private"` and `ttlMs: 60000`, and every `resources/read` result carries `cacheScope: "private"` and `ttlMs: 0`.<br>**Over stdio:** the v1.29.0 client's `initialize`, and a first message that claims no version, each get `-32022`. A message whose `_meta` claims `2026-07-28` but omits the client capabilities gets `-32602`. The server stays up across messages, with no per-message restart | a 2026-07-28 client can't connect, call or read; a 2025-era or malformed request gets anything but its own error, or causes an effect; a route rejects or echoes a session ID; a cache field is missing or has another value. A handler left on the default `legacy: "stateless"` fails the v1.29.0 control; one that skips header validation fails the `-32020` control; one that demands `Mcp-Name` everywhere fails the discover and list controls |

The 2025-era server is reached on its own version. **Inbound is unchanged:** in the same run, row 10's controls still refuse a 2025-era client. **A live DeepWiki check** (its public server needs no account) lists DeepWiki's tools through the gateway and makes one read-only call. It runs by hand or on a schedule, not in every CI run, because it depends on an outside service, and each run records the version DeepWiki advertised | the 2025-era server's tools are missing or fail; the 2026-07-28 server receives an `initialize` or is downgraded; a 2025-era client is accepted on a route we serve; DeepWiki's tools are missing or its call fails |

| 13 | The Worker behaves like the proxy | **Old-versus-new:** the same configuration and calls go to the proxy at `08f9e426` on a machine and to the Worker, both pointed at the same controlled remote test MCP server. Tool lists, results, refusals and the bytes of `describe`'s helper are compared item by item, in both modes, within today's limits. **Expected differences, each with its own case:** in `direct` the Worker also lists the four search tools (row 1's rule); calls past the Worker's own limits are refused (row 15). **One use, deployed:** two copies of the Worker are deployed under different names, sharing the same workspace objects. The same token goes to both at once, then again after redeploying; the test server counts effects. A build that remembers used tokens in a copy's memory fails, because the two copies share no memory. **Failure, local:** the workspace's object is made to fail, then to stall, when recording a token | any result differs outside the expected differences, including one byte of `describe`'s helper; a token's calls run more than once; any call runs when recording its token failed or stalled |
| 14 | Only members, and each workspace kept apart | **Deployed,** with two test organizations; the first holds two workspaces. All three workspaces use the same agent and server names but different credentials, and the test server records which credential each call arrived with. Tokens come from the real sign-in service. Refused cases, each with zero effects: no token; a forged token; an expired token; a token issued for another service; a token for one workspace sent to its sibling workspace's address in the same organization; a token for a workspace in the other organization; a valid token whose agent is no longer a member (removed after the token was issued), on its next call; and an agent sending another agent's name and session ID. A member whose persona leaves out one of the workspace's tools can't list or call that tool. **Controls:** an allowed call succeeds; the call with false labels runs as the sending agent, with its own tools and credential; and, once the sign-in change lets one agent be in two workspaces, an agent removed from one workspace still works in the other. **Structural:** the MCP route's code holds only the membership read port, so no request on it can add or remove a member | any refused case is served; a call arrives with another workspace's credential; a removed member's next call runs; removal stops the agent in another workspace; a persona's excluded tool is listed or runs; the false labels give the sender another agent's tools, connection or effects; anything on the MCP route writes membership |
| 15 | The Worker's own limits hold | Requests just under and just over each limit, locally and deployed: a 4 MiB body against one byte more; 50 calls against 51; a batch of 12 slow calls while the test server counts calls in flight; upstream responses that sum past 16 MiB. **Memory under overlap:** several of those requests held open together. Locally, Cloudflare's runtime runs them in one isolate. Deployed, Cloudflare doesn't promise which isolate serves a request, so each isolate logs a random, non-secret ID with every request. A run counts only when the logs show the requests active together in the same isolate; any other run is inconclusive, not a pass | a limit moves; more than 6 calls of one batch are in flight; the Worker fails, or Cloudflare reports exceeded memory, instead of returning too-large results, in a run where the requests overlapped in one isolate |
| 16 | Analytics carry nothing private | **Exact, local:** a capturing analytics binding records every data point written. Canary values go in arguments, results, secrets and tokens, plus very long and multibyte organization, workspace, server and tool names. A build that writes twice, writes nothing, leaks a canary or passes a byte limit fails. **Deployed:** Analytics Engine's SQL API shows that data arrives in the expected shape. Because it samples, it proves neither exact counts nor that nothing leaked, and it isn't used to. **Logs:** the Worker's logs are searched for the canaries | locally, a canary appears, a call writes no data point or more than one, or a point passes 96 bytes of index or 16 KB of text; a canary appears in the logs; a failed analytics write changes a call |
| 17 | Only people administer | **Locally and deployed,** against the owner's agent-management route (the one management route today). Refused cases, each followed by a direct read of the workspace's membership and the sign-in records showing nothing changed: a bot's agent token; a validly signed management-audience token with no person session; and a person's token whose session has been revoked. **Control:** the owner signs in through the CLI's interactive flow (authorization code with PKCE and a loopback redirect: a provider fixture locally, the sign-in Verification Design's test identities when deployed), a management command succeeds, and after that session is removed the next command is refused. A build that accepts an agent's token, or skips the live check on a later command, fails | an agent token or a token without a person session changes anything; a command succeeds after its person's session is gone |

## What stays unproven

- **Real third-party MCP servers.** Tests use controlled test servers; Gmail, GitHub and others aren't called.
- **Clients beyond the Portal SDK, the SDK v2 client and Claude Code.** Codex works only with its `mcp_2026_07_28` feature on; it isn't tested here, and neither are other harnesses. Users who opt Claude Code out of the new protocol will be refused.
- **Code mode.** It's not in this work.
- **Agent sign-in itself.** The sign-in service proves it in its own Verification Design (its `U8` section); rows 13 to 17 use its real tokens.
- **Router agents' identity** (F-77). How a Router vouches for its sessions isn't designed, so rows 14 and 17 use bots' own sign-in only.
- **One agent in several workspaces.** It waits for the sign-in change that gives an agent's client one link per workspace; until then row 14 skips that control.
- **How strong the admin human check is.** The owner hasn't decided it; row 17 proves the remembered sign-in with a live check, which the first build implements.
- **Per-user and computer tools.** They aren't built in this work.
- **1Password service-account tokens inside a Worker.** Cloudflare secrets are used instead.
- **Which clients defer and follow pages, beyond Claude Code.** Codex defers by default but refuses a list over 2,048 tools; Hermes defers only when configured to; Cursor documents neither. Each is set to `client-deferred` only after a real run like row 2's, against a catalog its limits cover.
- **The Worker's limits under real traffic.** The checks above prove each limit holds; they don't prove the numbers suit real use.
