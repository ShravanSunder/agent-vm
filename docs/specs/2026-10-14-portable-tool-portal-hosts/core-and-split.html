Tool Portal: core and split

- **Two core packages hold the logic.** `tool-access` decides who may use what. `tool-engine` serves tools to agents and runs each call through backends handed to it. Neither imports a platform, agent-vm or Gondolin. - **Two runtime packages bind that core to a platform:** `tool-host-node` for a Mac or Linux machine, `tool-host-cloudflare` for a Worker. - **Execution stays in agent-vm and is injected.** The Tool VM runner, managed VMs and Gondolin plug in as a backend. Tool Portal never sees a VM provider. - **A console service owns the UI** and talks to both Tool Portal and the fleet. Tool Portal serves only its control API; the request router and its model live in the console. - **Every one of the 117 current files has a destination.** About a fifth stay in agent-vm, a fifth retire, and the rest port into the four packages and the UI package. - **Decided (F-58, relayed by the Router/board Lead):** the extracted packages and the console live in a new monorepo, `agent-collaboration/agent-fleet-tools`, beside `agent-fleet-sync`. - **Who hosts the access screens and the request router:** the console service (recommended), or Tool Portal for now. - **D8, the router model.** In a frozen test of 16 requests, Haiku matched 14 and one Jev setup matched 4. Jev was about five times faster, but twice it added a removal nobody asked for. The design works with either, because a manager always Accepts; which one to pilot is yours. - **D6** (where the audit log lives and how long it keeps entries) and **D7** (whether agents' per-call approvals appear in this UI) are still open. Marks: ✅ you decided it (F-n in the [Fleet decisions](../2026-10-18-fleet-framework/2026-10-18-fleet-framework.md)); 🟡 the Lead's design proposal.

The packages

Five packages, plus two things outside them. Each arrow shows who calls or composes whom. The split is ✅ F-51 and F-52; the console is 🟡 under your provisional F-57. Owns the UI and composes `tool-access-ui`. Calls Tool Portal and the fleet. Runs the request router and its model. Owns no truth. Dispatch, MCP gateway, outbound connectors and the control API. Contracts, the access assessment, approval rules and credential rules: usable without the engine. Node listeners, stdio, local stores, config loading, catalog build, native and CLI backends. Worker request binding, Access verification, Durable Object stores and a remote-executor backend. Components for Tool Portal's places and the proposal card. Imports no server code or model SDK. Its managed composition builds Tool Portal the way a host does and injects the Tool VM runner backend. Managed VMs and Gondolin stay behind it; Tool Portal never sees a VM provider. Each package entrypoint gets a check that its published files load without `node:*`, a host, agent-vm or Gondolin wherever the rules forbid them. That check is what lets the four packages move to another repo later.

What the core does

- **contracts:** every shape that crosses a boundary, published once as a language-neutral artifact. The manifest and generator move here from agent-portal-sdk. - **authorization:** `assessAccess`, plus today's pure policy helpers moved unchanged: tool selectors, namespaces, MCP approval policy and CLI allowances. - **approval-rules:** exact-intent decision rules and their interfaces. The old HMAC approval tokens retire. - **credentials:** what an integration needs and which account may be selected, without holding any secret. - **dispatch:** plans each call and runs it through neutral backend, approval and operation interfaces. - **mcp-gateway:** what agents see over MCP: full and compact discovery, catalog and search. - **connectors:** calls out to registered HTTP MCP servers. - **control:** the control API (explain, propose, decide, read). It applies an accepted change once, together with its audit entry.

One tool call through the core

The host verifies the caller: from configuration now, from the fleet later. The gateway calls `assessAccess` in-process, a pure function over facts and the exact call, which answers usable, approval each call, blocked by policy, or not usable. Only approval each call goes to the approval authority, which returns a receipt bound to that exact call. The backend, injected by whoever composed the host, runs its own final checks before any effect. The result is completed, pending, denied or ambiguous. The console's access view calls the same `assessAccess`, so what an operator sees is what admission decides.

The seam that makes the split real

Today Tool Portal's backend and approval interfaces carry agent-vm's managed types, so it can't leave agent-vm yet. The target replaces them with neutral interfaces, and agent-vm's adapter keeps its own checks. 🟡

Backend call

The backend receives agent-vm's managed dispatch authority, so the managed proof travels through Tool Portal.

Approval

Tool Portal reserves and arms agent-vm's managed approval intents and reservations.

Accounts

Account availability takes agent-vm's managed invocation context.

Operation ids

Managed operation ids and fingerprints are computed inside Tool Portal.

Backend call

The backend gets an operation key, the exact capability and arguments, a verified-context reference and an approval-receipt reference. agent-vm's adapter rebuilds its own dispatch authority and re-checks principal, snapshot and assignment. A failed check refuses.

Approval

A neutral approval interface (challenge, decision, receipt) and operation interface. Reserve and arm stay at agent-vm's controller.

Accounts

Account facts come from the controller's Google policy service and broker, which stay their owners.

Operation ids

Managed ids and their exact bytes stay at agent-vm's adapter. Public operation keys are a new contract; nothing is aliased.

One answer for the access view and for admission

An access path is one agent and one tool in one workspace. Its state is **usable**, **approval each call**, **blocked by policy**, or **not usable** with the first unmet condition (✅ F-42). When the answer depends on the call, such as which Gmail operation or which account, the view shows a breakdown plus the rule that decides each call. At admission, today's validators check the exact call's arguments, so a denied flag or input is caught even when the command itself is allowed. The order below is 🟡, taken from what admission already does: 1. registration revoked (once workspaces are configured); 2. not allowed in the workspace (once workspaces are configured); 3. not given to the agent; 4. the tool's own deny rule, including a denied command, flag or input: **blocked by policy**; 5. account not granted; 6. account policy paused while a change applies; 7. the account policy's deny rule: **blocked by policy**; 8. provider consent missing or expired; 9. service unavailable; 10. otherwise **approval each call** if any rule says ask, else **usable**. The first step of the build assesses today's agent profiles, which have no workspaces yet; steps 1 and 2 apply once the configuration adds workspaces, and the system never pretends a workspace allows something it has not recorded. One fact is new: today's Google evaluator reports a paused account policy as "unavailable". The account authority will now supply the paused state separately, so the view never shows a paused account as broken or as missing consent.

Where it lives and when it moves

1. Build the four packages inside agent-vm's workspace, with the import check on from the first commit. 2. Rewire agent-vm's managed composition to the neutral interfaces. Its existing tests must pass through them. 3. Move the four packages to `agent-fleet-tools` (F-58), where the console will live too. Because the import check already holds, this is a directory move, not a refactor. Dependencies run one way: agent-vm uses Tool Portal, never the reverse. So `tool-host-node` gets secrets through an interface that agent-vm fills, instead of importing agent-vm's secret library. Whether the credential broker leaves agent-vm's controller is a separate decision. Until the fleet's identity contract exists, configuration lists workspaces, member agents, managers and registrations (✅ F-53). Each manager is a verified person, checked by issuer and subject; a service token or session label is never a manager. Tool policy still changes only through a proposal and a manager's Accept.
