# Concept walkthroughs

These paths teach the proposed system by concept. They reference the existing content where it belongs, including diagrams and specific nodes, and connect each need to its meaning, consequences, owners and proof. They do not select open architecture decisions or create another normative design.

## Understand the system

Follow your goal through identity, permissions, routing, credential custody, approval, recovery and the resulting package changes.

1. [Goal — your agents, your resources](requirements.html#requirements--diagram-1) — You want agents on different harnesses and machines to use your resources through MCP. Keep that outcome in mind: hosting, tool placement and agent identity must vary without rebuilding the security model. First see the shape that follows from this need.
2. [Composition — why there are two MCP levels](mcp-portal-explainer.html#gateway--diagram-1) — Your cloud entry connects ordinary providers, protected cloud services and computer services. The computer service exposes its configured tools; it need not use Gondolin. Collaboration stays independently governed. Before deciding what any caller can see, we need to know who that caller actually is.
3. [Identity — the requirement](requirements.html#requirements--agent-and-machine-identity) — Your identity requirement is more than naming a session. The same agent may reconnect or run elsewhere, while a stolen deployment credential must be revocable. This need forces us to distinguish the agent from its machine, credentials and conversations.
4. [Identity — the relationships](2026-10-14-portable-tool-portal-hosts.html#specification--diagram-2) — Here those distinctions become a precise model: a stable caller can have several credentials and sessions, with a current assignment. Rotation changes the proof, not the agent. The next question is how a real connection establishes that identity.
5. [Authentication — turn proof into an enrolled agent](program-design.html#program--example-provision-an-agent-without-a-new-identity-provider-product) — The shared backbone is the intended identity home. You authorize agent types and launchers; a launcher enrolls instances automatically. The gateway still needs verified agent proof and a current assignment. Cloudflare machine/service admission and Router session labels do not supply that agent proof; its contract and ingress carriage remain open.
6. [Authentication — check which identity survives the entry](mcp-portal-explainer.html#gateway--the-cloudflare-identity-constraint) — The enrollment example assumes a proof that actually reaches our gateway. Cloudflare’s managed Portal uses a configured admin credential for unattended upstream access, so original-agent identity cannot be assumed. This constraint must be resolved before caller-specific permissions can work through that entry.
7. [Permissions — knowing the caller is only the beginning](2026-10-14-portable-tool-portal-hosts.html#specification--c1-mcp-discovery-and-invocation) — Once identified, the agent sees only its permitted capabilities. Guessing a hidden tool name must fail too. Full catalog and compact search are alternative presentations of the same permissions, so client convenience cannot become a second authorization path.
8. [Workspace — scope each call deliberately](2026-10-14-portable-tool-portal-hosts.html#specification--c10-workspace-context-and-team-resources) — A bot may discover the union of its workspace tools, but each call names one admitted workspace and fits that workspace’s allowance. That selector is not identity proof. Managers configure team-account use; requester attribution never supplies personal credentials. The next step follows this permission model into routing.
9. [Resource groups — one URL need not mean one permission set](mcp-portal-explainer.html#gateway--one-address-can-expose-different-groups) — When the entry preserves verified per-agent identity, that policy can expose ordinary search to one agent and sensitive or computer tools to another through the same address. Separate endpoints are an isolation option, not the permission model. Now follow an allowed computer call beyond the cloud gateway.
10. [Routing — preserve the caller across the hop](2026-10-14-portable-tool-portal-hosts.html#specification--c6-cloud-to-computer-composition) — The computer must recognize both the acting gateway and the represented agent, then enforce its own ceiling. Being reachable is insufficient. This explains why a gateway connection needs bounded delegation and the same represented caller/item at the computer. Its target and inner key are recorded before forwarding, even if the reference has not returned; a copied agent-name field cannot supply that authority.
11. [Placement — different hosts compose different effects](program-design.html#program--what-runs-where) — A Worker can route HTTP MCP and evaluate portable policy; a Mac can host native effects; the managed controller retains its protected VM operations. These placements answer your portability requirement. They do not require every host to import the same desktop or execution runtime.
12. [Credentials — authority stays beside the resource](tool-portal-explainer.html#security--where-credentials-run) — The backend selects the provider account and uses its grant. The agent gets the permitted result, not the provider credential. Several controlled CLIs may share a backend. This custody boundary is separate from the credential the agent uses to connect to MCP.
13. [Approval — your requirement is reusable decision presentation](requirements.html#requirements--approval-surfaces) — Some otherwise permitted actions need an exact decision. You want that request to appear in Hermes, Router, the IDE or another surface. That requirement cannot be met by moving a Hermes-specific prompt into the dispatcher; we must separate the jobs first.
14. [Approval — library, authority and presenter](program-design.html#program--approvals-library-authority-and-presenter) — The library defines decision rules, an authority stores the decision, and a presenter shows it. A webhook delivers a notification. Sharing the library does not make every presenter a decision writer. With those responsibilities separate, the protected-call sequence becomes understandable.
15. [Approval — follow one exact action](tool-portal-explainer.html#security--a-protected-call) — The tool service creates a challenge for one operation, reports pending, and continues that same operation only after a valid decision. Approval never overrides a hard deny. The next stop addresses the return path: how does the authority authenticate the operator or client submitting the decision?
16. [Approver identity — the return path is protected too](program-design.html#program--how-a-human-decision-reaches-a-cloud-or-mac-authority) — An operator session or explicitly enrolled approver client authenticates the decision’s source. Client-key possession alone does not prove a fresh human gesture; the client is part of the decision trust boundary. A presenter cannot simply claim the owner clicked approve. A Mac authority also needs this protected return path.
17. [Router integration — reuse what exists and expose the gap](program-design.html#program--router-integration-reuse-the-boundary-not-declared-actors-as-authentication) — Router has useful typed interactions and adapters, but the inspected local broker uses declared actors and cancels pending interactions on restart. It can present a tool challenge through an explicit adapter; adopting it as remote authority needs additional contracts. Neither integration merges collaboration permissions with tool access.
18. [Recovery — a lost connection is not a new action](2026-10-14-portable-tool-portal-hosts.html#specification--c4-recovery-without-effect-replay) — Your logical-session requirement now matters at the effect boundary. If a response disappears after dispatch, reconnecting must recover the same operation or its ambiguity. Repeating an uncertain action under a fresh wrapper would violate the outcome you asked for.
19. [Recovery — when the Mac reply never arrives](program-design.html#program--recover-the-inner-reference-after-a-lost-reply) — The Mac may have created or completed work before the gateway learns its reference. The gateway already retained the target and same caller/item key. Recovery finds that record; it cannot generate a new item or call the executor just to learn what happened. Current delegation and lookup permission still apply. This closes a failure window before ordinary result lookup is possible.
20. [Durability — what must survive the process](program-design.html#program--durable-state-failure-and-concurrency) — The operation owner persists reservation, arming and known outcomes. Once armed, a missing receipt cannot be treated as non-execution. This is why portable state-machine code needs a real durable adapter, and why a process-local replay map cannot establish distributed safety.
21. [Shared components — the extraction requirement](requirements.html#requirements--shared-security-consumers) — These concepts must also be usable outside either portal runtime. That is your separation-of-concerns requirement: identity, policy, credentials and approval cannot depend on a particular MCP listener, desktop or VM provider. The package boundaries follow from those independent consumers.
22. [Packages — give each responsibility a home](program-design.html#program--diagram-2) — Hosts compose MCP Gateway and Tool Portal. One shared tool-access package contains separate contract, authorization and approval-rule modules; each can be consumed without importing a portal runtime. That preserves your independent-use requirement without publishing a package per rule family. HTTP MCP connectors own outbound protocol work.
23. [Shared contracts — cross languages without copying meaning](program-design.html#program--contracts-across-typescript-python-rust-and-swift) — The shared contracts module owns one manifest, generator and fixture corpus; the SDK becomes a consumer. Managed and new public families stay distinct, so a valid managed message cannot be mistaken for a public decision. Rust and Swift validate the expected family/version from that artifact. Representation parity still does not prove authenticated decisions or durable consumption.
24. [Code delta — distinguish moving code from new behavior](program-design.html#program--current-code-and-the-required-change) — The source map says what stays, moves, is added or is retired. Splitting Node imports is extraction; durable public operations and verified distributed identity are additional behavior. Existing managed controller, credential and generation checks remain obligations through either kind of change.
25. [Administration — connect the screens to their owners](program-design.html#program--workspace-configuration-and-the-react-control-surface) — React owns the draft and its feedback. Protected host routes verify the operator and revisions; policy and credential owners apply the change. The audit occurrence belongs to the authoritative security commit. A fixture save cannot prove those integrations. The old Hono presentation is replaced only after the complete consent and policy workflows preserve their security checks.
26. [Cutover — retire old authority without inventing history](program-design.html#program--retire-legacy-standalone-approvals) — The new host retires both legacy standalone approval protocols. Their tokens never become new grants, and an uncertain old call never becomes a fresh retry automatically. Old maps are not a durable ledger. The operator accounts for work per item, preserves existing managed history and keeps affected capabilities unavailable until unresolved effects are reconciled. This is a cutover design, not proof of deployed retirement.
27. [Interoperability and cost — choose mechanisms deliberately](program-design.html#program--standards-alignment-without-claiming-unimplemented-conformance) — The shared boundaries cross products and hosts, so use established protocol contracts where they fit. MCP rules, webhook delivery and the approval draft address different parts of the system. They do not make every client compatible or every mechanism free: Cloudflare Access mTLS requires a paid plan. No new issuer or paid tier is selected.
28. [Identity proof — catch the wrong implementation](verification-design.html#verification--j8-enrollment-and-revocation) — Return to your identity need and ask what would falsify the design. An untrusted agent copying a session name must fail; rotating a credential must preserve logical identity; revocation must meet its selected freshness bound. These observations are planned, not already demonstrated.
29. [Approval proof — delivery is not the outcome](verification-design.html#verification--j9-approval-surfaces-and-router-isolation) — Your reusable-approval requirement is met only when the actual surface returns an authenticated exact decision and the effect obeys it. Duplicate notifications, a declared actor or a delivery acknowledgement must not approve. A mock presenter cannot establish the real Router or IDE integration.
30. [Workspace and audit proof — observe the actual authority](verification-design.html#verification--j11-workspace-administration-named-calls-and-react-cutover) — Test two workspaces, forged selectors and direct API attempts, then observe the protected React workflow and authoritative activation. J12 follows with audit recovery across failure. A consistent screenshot or toast cannot establish permission enforcement or durable history.
31. [Open choices — what the model still needs from you](requirements.html#requirements--decisions-that-remain-open) — We can now see why the remaining choices matter: identity and ingress determine whose proof survives; approval placement determines its control and continuation path; source-machine policy and freshness bounds determine exposure. Cost and standards fit belong in those choices too. They remain open decisions; the walkthrough explains consequences without silently choosing a mechanism or paid tier.

## Identity and permissions

Connect agent and machine identity to enrollment, Cloudflare proof, caller-specific access and the checks that must hold.

1. [Identity starts with your requirement](requirements.html#requirements--agent-and-machine-identity) — You want an agent to remain identifiable across sessions and machines, while retaining separately revocable credentials. That is the need this path follows; a displayed agent name or Router session is not yet its authentication mechanism.
2. [Separate the identities](tool-portal-explainer.html#security--who-is-who) — Agent, machine, service, credential and session answer different questions. Keeping them separate prevents key rotation or reconnect from accidentally becoming a new agent. Now see how those concepts relate, rather than treating them as five unrelated labels.
3. [The relationship that survives rotation](2026-10-14-portable-tool-portal-hosts.html#specification--diagram-2) — One caller may have several issued credentials and session associations, with one current assignment per addressed scope. Separate credentials are revocation units; they do not automatically create private histories within one logical agent. Current lookup policy still applies.
4. [Enrollment connects proof to the agent](program-design.html#program--example-provision-an-agent-without-a-new-identity-provider-product) — The owner authorizes an agent type and launcher; the launcher enrolls each launched instance through the intended shared backbone. Its credential proves the instance, while each product owns its permission assignment. The enrollment and credential-carriage contract remains open. A session identifier cannot substitute for it today.
5. [Check the actual Cloudflare entry](mcp-portal-explainer.html#gateway--the-cloudflare-identity-constraint) — The managed Portal's documented unattended path uses an upstream admin credential. Our gateway cannot assume distinct agents survive that hop. Access-direct and explicitly separated managed registrations are design options; the entry architecture must preserve the identity the previous stop established.
6. [Turn identity into allowed work](2026-10-14-portable-tool-portal-hosts.html#specification--c1-mcp-discovery-and-invocation) — Authentication identifies the caller. Its complete assignment determines allowed discovery, invocation and lookup. This is where your different-agent access requirement becomes a rule every MCP presentation must enforce, including guessed or stale tool references.
7. [Carry only bounded authority onward](2026-10-14-portable-tool-portal-hosts.html#specification--c6-cloud-to-computer-composition) — On the next service hop, the resource verifies the gateway actor and represented agent, then applies its own ceiling. A valid cloud login does not automatically grant a computer effect. Delegation must preserve this distinction, not forward an unverified identity object.
8. [Prove the distinction under misuse](verification-design.html#verification--j8-enrollment-and-revocation) — Test enrollment, spoofed labels, separate credentials, rotation and revocation against the selected real issuer and target. The operation's history must survive a credential change. The selected source-machine and freshness policies provide the reference limits; they have not been chosen yet.
9. [Locate the remaining identity choices](requirements.html#requirements--decisions-that-remain-open) — The shared backbone direction is selected; its persona/instance semantics, issuer/bootstrap contract, ingress proof and freshness policy still need definition. Source-machine restrictions are a separate decision. Client compatibility, source-proof cost and standards fit remain part of that decision. Those gaps prevent treating the design as a deployed identity service.

## Approvals across products

Follow one protected action from your reusable-approval requirement through authority, presentation, authenticated decision and recovery.

1. [The requirement is one approval meaning across surfaces](requirements.html#requirements--approval-surfaces) — You want Hermes, Router, the IDE or another integration to show the same protected request. The need is reusable decision meaning and routing, not a requirement that every product owns the same writable approval database.
2. [Establish the responsibilities](program-design.html#program--approvals-library-authority-and-presenter) — Separate the engine, authoritative record, presenter and notification transport. A webhook can connect products without becoming permission to act. Next make the decision concrete: what precisely is the human being asked to approve?
3. [Bind the decision to exact work](2026-10-14-portable-tool-portal-hosts.html#specification--c2-exact-protected-action) — The approval binds one operation, exact current intent and requesting credential issuance. Changed arguments or another issuance cannot consume that existing grant for first dispatch. Policy denial remains denial, so approval is not an alternative privilege system.
4. [See the interaction across owners](program-design.html#program--the-approval-boundary-inside-that-call) — The computer asks its selected approval authority; a human sees a redacted challenge through a presenter; the decision returns to its authority. This is the interaction an adapter must preserve. The authority may be local or external, which remains a deployment decision.
5. [Authenticate the human decision](program-design.html#program--how-a-human-decision-reaches-a-cloud-or-mac-authority) — The decision route verifies an operator session or admitted approver client for its control audience. Router's ordinary service identity cannot assert that a human clicked approve. If the authority is on a Mac, a protected route to that authority is part of the same requirement.
6. [Understand Router's current integration limit](program-design.html#program--router-integration-reuse-the-boundary-not-declared-actors-as-authentication) — Reuse Router's typed interaction vocabulary and adapter pattern. Its inspected broker is not yet a verified remote exact-tool authority. Cross-machine continuation, authenticated decision actors and exact intent consumption must be supplied before selecting that role for it.
7. [Keep the operation when the connection disappears](2026-10-14-portable-tool-portal-hosts.html#specification--c4-recovery-without-effect-replay) — An approved action can still lose its response. The effect owner must preserve the same operation and return a known receipt or ambiguity. Neither a second notification nor a new connection permits an automatic second action.
8. [Retire old tokens without retrying old effects](program-design.html#program--retire-legacy-standalone-approvals) — The new contract accepts no legacy standalone approval authority or compatibility alias. Known managed history stays with its owner; missing standalone history is reported honestly. Closing a listener or waiting for token expiry cannot prove a backend did nothing. The affected capability stays unavailable until the cutover accounts for its old work.
9. [Prove approval at the effect](verification-design.html#verification--j9-approval-surfaces-and-router-isolation) — Exercise the real chosen surface, authenticated decision path and resource outcome. Forged actors, delayed or duplicate events and delivery acknowledgements must fail to approve. If Router becomes the authority, its durable continuation and consumption also need real proof.
10. [Leave the actual authority choice visible](requirements.html#requirements--decisions-that-remain-open) — The remaining approval decisions include which policy domain can require a separate gate, where the authoritative record lives, and how valid undispatched work continues after interruption or credential change. Neither ignoring a cloud approval requirement nor creating two prompts is a selected default. The integration must also fit the selected standards and operating cost. This walkthrough has exposed what each choice must preserve; it has not selected an authority, mechanism or paid tier for you.
