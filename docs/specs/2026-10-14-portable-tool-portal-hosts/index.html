Notification delivery does not approve. Goal — your agents, your resources. You want agents on different harnesses and machines to use your resources through MCP. Keep that outcome in mind: hosting, tool placement and agent identity must vary without rebuilding the security model. First see the shape that follows from this need. Composition — why there are two MCP levels. Your cloud entry connects ordinary providers, protected cloud services and computer services. The computer service exposes its configured tools; it need not use Gondolin. Collaboration stays independently governed. Before deciding what any caller can see, we need to know who that caller actually is. Identity — the requirement. Your identity requirement is more than naming a session. The same agent may reconnect or run elsewhere, while a stolen deployment credential must be revocable. This need forces us to distinguish the agent from its machine, credentials and conversations. Identity — the relationships. Here those distinctions become a precise model: a stable caller can have several credentials and sessions, with a current assignment. Rotation changes the proof, not the agent. The next question is how a real connection establishes that identity. Authentication — turn proof into an enrolled agent. The shared backbone is the intended identity home. You authorize agent types and launchers; a launcher enrolls instances automatically. The gateway still needs verified agent proof and a current assignment. Cloudflare machine/service admission and Router session labels do not supply that agent proof; its contract and ingress carriage remain open. Authentication — check which identity survives the entry. The enrollment example assumes a proof that actually reaches our gateway. Cloudflare’s managed Portal uses a configured admin credential for unattended upstream access, so original-agent identity cannot be assumed. This constraint must be resolved before caller-specific permissions can work through that entry. Permissions — knowing the caller is only the beginning. Once identified, the agent sees only its permitted capabilities. Guessing a hidden tool name must fail too. Full catalog and compact search are alternative presentations of the same permissions, so client convenience cannot become a second authorization path. Workspace — scope each call deliberately. A bot may discover the union of its workspace tools, but each call names one admitted workspace and fits that workspace’s allowance. That selector is not identity proof. Managers configure team-account use; requester attribution never supplies personal credentials. The next step follows this permission model into routing. Resource groups — one URL need not mean one permission set. When the entry preserves verified per-agent identity, that policy can expose ordinary search to one agent and sensitive or computer tools to another through the same address. Separate endpoints are an isolation option, not the permission model. Now follow an allowed computer call beyond the cloud gateway. Routing — preserve the caller across the hop. The computer must recognize both the acting gateway and the represented agent, then enforce its own ceiling. Being reachable is insufficient. This explains why a gateway connection needs bounded delegation and the same represented caller/item at the computer. Its target and inner key are recorded before forwarding, even if the reference has not returned; a copied agent-name field cannot supply that authority. Placement — different hosts compose different effects. A Worker can route HTTP MCP and evaluate portable policy; a Mac can host native effects; the managed controller retains its protected VM operations. These placements answer your portability requirement. They do not require every host to import the same desktop or execution runtime. Credentials — authority stays beside the resource. The backend selects the provider account and uses its grant. The agent gets the permitted result, not the provider credential. Several controlled CLIs may share a backend. This custody boundary is separate from the credential the agent uses to connect to MCP. Approval — your requirement is reusable decision presentation. Some otherwise permitted actions need an exact decision. You want that request to appear in Hermes, Router, the IDE or another surface. That requirement cannot be met by moving a Hermes-specific prompt into the dispatcher; we must separate the jobs first. Approval — library, authority and presenter. The library defines decision rules, an authority stores the decision, and a presenter shows it. A webhook delivers a notification. Sharing the library does not make every presenter a decision writer. With those responsibilities separate, the protected-call sequence becomes understandable. Approval — follow one exact action. The tool service creates a challenge for one operation, reports pending, and continues that same operation only after a valid decision. Approval never overrides a hard deny. The next stop addresses the return path: how does the authority authenticate the operator or client submitting the decision? Approver identity — the return path is protected too. An operator session or explicitly enrolled approver client authenticates the decision’s source. Client-key possession alone does not prove a fresh human gesture; the client is part of the decision trust boundary. A presenter cannot simply claim the owner clicked approve. A Mac authority also needs this protected return path. Router integration — reuse what exists and expose the gap. Router has useful typed interactions and adapters, but the inspected local broker uses declared actors and cancels pending interactions on restart. It can present a tool challenge through an explicit adapter; adopting it as remote authority needs additional contracts. Neither integration merges collaboration permissions with tool access. Recovery — a lost connection is not a new action. Your logical-session requirement now matters at the effect boundary. If a response disappears after dispatch, reconnecting must recover the same operation or its ambiguity. Repeating an uncertain action under a fresh wrapper would violate the outcome you asked for. Recovery — when the Mac reply never arrives. The Mac may have created or completed work before the gateway learns its reference. The gateway already retained the target and same caller/item key. Recovery finds that record; it cannot generate a new item or call the executor just to learn what happened. Current delegation and lookup permission still apply. This closes a failure window before ordinary result lookup is possible. Durability — what must survive the process. The operation owner persists reservation, arming and known outcomes. Once armed, a missing receipt cannot be treated as non-execution. This is why portable state-machine code needs a real durable adapter, and why a process-local replay map cannot establish distributed safety. Shared components — the extraction requirement. These concepts must also be usable outside either portal runtime. That is your separation-of-concerns requirement: identity, policy, credentials and approval cannot depend on a particular MCP listener, desktop or VM provider. The package boundaries follow from those independent consumers. Packages — give each responsibility a home. Hosts compose MCP Gateway and Tool Portal. One shared tool-access package contains separate contract, authorization and approval-rule modules; each can be consumed without importing a portal runtime. That preserves your independent-use requirement without publishing a package per rule family. HTTP MCP connectors own outbound protocol work. Shared contracts — cross languages without copying meaning. The shared contracts module owns one manifest, generator and fixture corpus; the SDK becomes a consumer. Managed and new public families stay distinct, so a valid managed message cannot be mistaken for a public decision. Rust and Swift validate the expected family/version from that artifact. Representation parity still does not prove authenticated decisions or durable consumption. Code delta — distinguish moving code from new behavior. The source map says what stays, moves, is added or is retired. Splitting Node imports is extraction; durable public operations and verified distributed identity are additional behavior. Existing managed controller, credential and generation checks remain obligations through either kind of change. Administration — one view, and change by asking. The access view and admission call the same assessment, so what a manager sees is what an agent gets. A request becomes a proposal that changes nothing until a manager of that workspace accepts it; the policy and account owners then apply it once, with its audit occurrence. The console that hosts these screens owns no authority. Cutover — retire old authority without inventing history. The new host retires both legacy standalone approval protocols. Their tokens never become new grants, and an uncertain old call never becomes a fresh retry automatically. Old maps are not a durable ledger. The operator accounts for work per item, preserves existing managed history and keeps affected capabilities unavailable until unresolved effects are reconciled. This is a cutover design, not proof of deployed retirement. Interoperability and cost — choose mechanisms deliberately. The shared boundaries cross products and hosts, so use established protocol contracts where they fit. MCP rules, webhook delivery and the approval draft address different parts of the system. They do not make every client compatible or every mechanism free: Cloudflare Access mTLS requires a paid plan. No new issuer or paid tier is selected. Identity proof — catch the wrong implementation. Return to your identity need and ask what would falsify the design. An untrusted agent copying a session name must fail; rotating a credential must preserve logical identity; revocation must meet its selected freshness bound. These observations are planned, not already demonstrated. Approval proof — delivery is not the outcome. Your reusable-approval requirement is met only when the actual surface returns an authenticated exact decision and the effect obeys it. Duplicate notifications, a declared actor or a delivery acknowledgement must not approve. A mock presenter cannot establish the real Router or IDE integration. Workspace and access proof — compare the view with admission. Test two workspaces and forged selectors, then compare every shown state with what admission decides for the same call and surface. J14 checks that only a manager's Accept applies a proposal, once, and J12 that every change is audited. A screenshot or toast cannot establish enforcement or history.
