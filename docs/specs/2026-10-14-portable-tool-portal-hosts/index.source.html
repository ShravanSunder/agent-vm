Tool Portal: take it apart and put it back together

- **Today's `@agent-vm/tool-portal` and `@agent-vm/mcp-portal` become pieces with one job each:** `tool-access` (the rules), `tool-engine` (shows tools and routes every call through one dispatcher), `tool-host-node` (runs it on a machine) and `tool-host-cloudflare` (runs the MCP proxy on a Worker). agent-vm plugs in through its own adapter. - **Behaviour stays the same.** The three ways in (agent-vm's private connection, the standalone Tool Portal and the MCP proxy) keep their tools, results, approvals and limits. - **Two cases, chosen for each client:** a client that loads tools lazily itself gets `direct` (every tool plus the search tools, sent in pages); any other client gets `indirect`, where the portal does the lazy loading through its search tools. - **The one addition is a deployed, secured Cloudflare Worker** serving the proxy for organization tools. Each organization has its own Durable Object for sign-in and used approvals, and each call sends one data point to Analytics Engine. Per-user and computer tools are designed for, and built after your decisions. - **Later:** code mode in both modes. UI, people sign-in, workspaces and audit belong to separate projects. 1. **Do agents reach the Worker through Cloudflare's MCP Portal, or directly behind Access?** For agents using service tokens through the Portal, as Cloudflare documents it, the Worker can't tell them apart. This blocks the Worker's caller check; it went to Sun as a brief. 2. **Who issues real sign-in and agent tokens: our own Better Auth service, or fleet?** This blocks per-user tools, and selling this without your Cloudflare Access. 3. **Do tool calls need history that survives a restart?** The design assumes not; the Worker keeps only which approvals were used. 4. **Retire either of today's two standalone approval paths?** The design keeps both. Deploying the Worker also needs a Cloudflare account and an API token.
