Tool Portal: take it apart and put it back together

- **Today's `@agent-vm/tool-portal` and `@agent-vm/mcp-portal` become pieces with one job each:** `tool-access` (the rules), `tool-engine` (shows tools and routes every call through one dispatcher), `tool-host-node` (runs it on a machine) and `tool-host-cloudflare` (runs the MCP proxy on a Worker). agent-vm plugs in through its own adapter. - **Behaviour stays the same.** The three ways in (agent-vm's private connection, the standalone Tool Portal and the MCP proxy) keep their tools, results, approvals and limits. - **The first version adds a deployed Cloudflare Worker** for team tools. Agents sign in with our own login (Better Auth, in its own sign-in Worker), each organization has one Durable Object for membership and used approvals, and each call sends one data point to Analytics Engine. - **Each client picks how tools are shown by its address:** `?tools=direct` gives the full list, for clients that search it themselves; the plain address gives only the search tools. - **Next:** per-user tools under today's permission model, computers reached through Cloudflare like Tailscale, and the chat-led change flow in the separate control UI. Code mode later, not blocked. 1. **Agents connect straight to our Worker and sign in with Better Auth,** not through Cloudflare's MCP Portal or Access. Cloudflare is only for reaching registered computers, like Tailscale. 2. **Better Auth issues logins and agent tokens,** from its own sign-in Worker. 3. **A URL parameter** (`?tools=direct`) picks how tools are shown. Still assumed unless you say otherwise: no saved history of tool calls, and both of today's approval methods are kept. Deploying uses your existing Cloudflare CLI login.
